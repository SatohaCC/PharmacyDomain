# DDD & Onion Architecture

業務上の不変条件を、その責務を所有するモデルと整合性境界で守る。依存グラフだけでなく、生成・復元・状態遷移、資源寿命、確定点を対象の契約に照らして確認する。

## 依頼と適用契約を先に決める

- 設計、実装・修正、レビュー、説明のどれを求められたか確認する。レビュー・提案だけならソースを変更しない。実装を依頼されたら提案だけで終えない。
- ユーザーの明示要件、適用AGENTS、承認済み設計、現行コード・テスト・依存検査を確認する。未承認案や現状の違反を、採用済み契約とは扱わない。プロジェクト固有の承認手順を守るが、このSkill自体は別の承認工程を追加しない。
- 下表は**本Skillの厳格な既定**。他プロジェクトの明示された許可範囲・言語・配置が異なれば、その契約を保持する。既存契約の変更が必要なら理由と影響を示し、通常の変更手順に従う。medi-chat等で採用済みの完全禁止を、一般論で緩めたりignore設定で通したりしない。
- ファイル数・クラス数を目標にしない。読み取りだけのQuery、薄いCRUD、一時的な集計にRepository・Aggregate・UoW・イベント基盤を一律に追加しない。業務ルールや整合性境界がある箇所に必要なモデルを使う。

## 作業の進め方

1. **対象と根拠**: 今回の契約、変更可能範囲、公開入出力、検証入口を特定する。資料がない部分は仮定として示し、判断に必要な不足だけ確認する。
2. **所有権**: 業務ルール、ID・原本・派生モデル、ユースケース、技術資源をそれぞれ誰が所有するか決める。単なる保存テーブル・コードの再利用単位を集約やコンテキストと同一視しない。
3. **経路を追う**: 外部入力 → 境界検証 → 明示変換 → ユースケース → 業務判断 → 保存/確定 → 公開結果まで、失敗経路も追う。並行更新・再試行・外部副作用があるときは、その保証範囲まで確認する。
4. **依頼に応じた成果物**を作り、関連する構造検査と振る舞いを確認する。読了やimport成功だけで、業務上の正しさ・実DBの原子性・通信成功を判定しない。

## 依存の既定

表は直接のソース依存を示す。実行時にPort経由で外部へ呼び出すことと、具象をimportすることを区別する。間接依存・再公開・動的importまで何を検査するかは、対象の契約と検出能力で確認する。

| 層 | 所有するもの | 既定の依存先 |
|---|---|---|
| Domain | 値、業務判断、状態遷移、集約の不変条件、必要なRepository抽象 | 標準ライブラリとDomain内の許可されたモデル。外層/DB/FWには依存しない |
| Application | ユースケース、外部Port、入出力・失敗契約、確定方針 | Domain、Application内の許可された契約、標準ライブラリ。Config/Infra/FWには依存しない |
| Infrastructure | Repository/Port実装、DB/SDK/外部形式との変換 | Application/Domainの抽象と必要な技術・設定 |
| Presentation | 公開DTO、形式検証、Applicationへの委譲、公開エラーへの変換 | Applicationと外側のWeb技術/必要なConfig。Domain/Infraを直接importしない |

Composition Rootはこれらを組み立てる外側の起動点。内層から依存させない。名前を変えた再公開や同等ラッパーで禁止依存を迂回しない。

## 保持する設計方針

- 単一値の意味・検証はPrimitive、**利用文脈の業務制約**と組み合わせの整合性はVO/Entity/Aggregate。型確認の反復を削っても、必要な業務検証は削らない。
- 型付け済みの値と不変コレクションを明示して生成する。変換だけのcreateラッパー、__post_init__内の暗黙変換、原文への一律trim/NFKCは追加しない。復元でも不変条件を守る。
- Domain/ApplicationはDTO・ORM・SDKモデルと兼用しない。Pydanticは外側の入力・出力・設定境界で使い、変換を明示する。
- IDと業務語彙は所有元を持つ。Shared Kernelは意味・制約・変更責任の合意があるものだけ。原本と派生モデルは用途・不変条件・ライフサイクルで区別する。
- 同じ意味・契約の操作に同等ラッパーや迂回経路を増やさない。目的や契約が異なるPort・境界変換・復旧処理は、重複APIと混同しない。

## 成果物と完了の判定

- **設計**: 要件/不変条件、所有層と依存、境界型・Port、失敗/整合性契約、既存からの変更範囲、受入条件を示す。必要な論点だけを扱う。
- **レビュー**: 実在するfile:lineまたは入力の位置、適用契約、観測できる影響、最小の是正、確認方法を示す。証拠のない欠陥や件数合わせの指摘を作らず、問題がなければ「指摘なし」と範囲を述べる。未提示のcommit/失敗分類/HTTP mapping等は確認事項とする。望ましい設計との違いだけでは欠陥とせず、今回の契約違反と影響を示す。
- **実装**: 対象と利用側・テストを整合させ、合意した不変条件・入出力・失敗を検証する。ファイル移動やlint成功を振る舞いの成功で代替しない。
- コマンド・場所・結果、確認した層、未実施/skip/環境不足を分けて報告する。Fakeでの成功を実DB、外部API、並行実行の成功に拡張しない。
