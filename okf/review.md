# コードレビューの方針

品質ゲート（`pytest` / `mypy --strict` / `ruff`）の通過は出発点であり、レビューの結論ではありません。
ゲートが機械的に検出できない設計上の欠陥を見つけることがレビューの目的です。

## 0. 最優先原則: 規約ではなく仕組みで守る

- 指摘のたびに「これは規約で守られているか、仕組みで守られているか」を明示する。
- 規約で守られているものは、**壊れたら自動的に落ちる形**への置き換えを提案する。
- 仕組みの優先順位: 型 → データ構造 → テスト → 静的チェッカ → 起動時の `raise`。
- ドキュメントへの追記は最後の手段。機械化できないと判断したときだけ選ぶ。
- 「レビューで気づけばよい」は仕組みではない。人が変われば消える。
- 機械化しない判断も明示する。全部を機械化すると保守コストが勝つ。

### 規約の兆候

- 「〜を忘れずに呼ぶ」「〜の順で書く」「〜は作らない」といった説明が必要な設計。
- 手順書やコメントにしか存在しないルール。
- チェッカを作ったが、どのゲートからも呼ばれていない状態。

## 1. 依存関係

- 宣言上の依存の向きではなく、**import の到達可能性**で結合を判断する。
- パッケージの `__init__.py` は副作用を持つ。サブモジュールを直指定しても必ず実行される。
- 「今は循環していない」と「循環しえない」を区別する。前者は指摘対象。
- 依存を持たない leaf に切り出せているものは、その状態が維持される仕組みがあるか確認する。
- モジュールの docstring と中身が一致しているか。名前が実態と乖離し始めたら置き場所が誤っている。
- 依存の向きは、ドキュメントではなく静的チェックで強制する。

## 2. 後からの壊れやすさ

今のコードが正しいかではなく、**次に触る人が壊せるか**で判断します。

- 分類やフラグを追加し忘れたとき、拒否側（fail-safe）に倒れるか、許可側（fail-open）に倒れるか。
- 同じルールが2箇所に実装されていないか。片方が呼ばれていない二重実装は、壊れても気づけない。
- デッドコードは掃除の問題ではなく、**変更を検知できない領域**として扱う。
- 順序に依存する構造（例外の捕捉順、初期化順、MRO）は、順序が無関係な構造に置き換える。
- Composite Value Object / Entityの具象サブクラスが`__post_init__`を上書きして共通型ガードを迂回していないか。正規化と業務検証はフックへ置く。
- dataclassフィールドに継承専用の`Base*` Domain Primitiveや未解決TypeVarが残っていないか。tuple内要素まで実行時に照合されるか。
- 実行環境やビルドフラグで挙動が変わらないか。`assert` は最適化フラグ下で消えるため、不変条件の強制には使わない。
- 暗黙の前提は必ず踏まれる。明文化ではなく、踏めなくする。

## 3. 明示性

判断軸は「**この宣言だけを読んだ人が、正しい実装を書けるか**」です。

- 受け取っているのに判定に使われていない引数がないか。
- 分類が否定形（「Aに含まれないこと」）になっていないか。集合を明示し、網羅性と排他性を起動時に検証する。
- デフォルト値が意味を持ってしまっていないか（識別子の既定値は監査を潰す）。
- 常に真になる条件が「二重に守られている」と誤読させていないか。残すなら意図をコメントする。
- 公開範囲（`__all__`、パッケージの再エクスポート）が実際の利用と一致しているか。
- docstring の `Raises:` が実際に送出される例外と一致しているか。
- Commandへ記録者・記録時刻のような信頼済み監査値を混入できないか。認可Actorと注入Clockが同じ経路で使われるか。

## 4. テストが実際に保証しているもの

- 緑であることと、守られていることは別。
- テストダブルが現実を隠していないか。常に成功を返す Fake は、そのぶん検証範囲を消している。
- read-check-writeの一意性テストだけで原子性を主張していないか。Repositoryのsave最終検査と本番DB制約を区別する。
- 履歴の再検証がSnapshot値だけで済んでいないか。元資格ID列と再構築値の双方を比較し、欠落や別IDを見逃さないか。
- 用意した仕掛けが実際に使われているか。呼び出し元のないテスト用 API は、無検証領域の裏返し。
- 1テスト1振る舞いか。複数の Act を詰めると、失敗しても原因を特定できない。
- 「呼び忘れ」「取り違え」を検知するテストがあるか。無ければ、その規約は守られていない。
- テストの不在それ自体を指摘対象とする。

## 5. ドキュメント

- `okf/` はコードと同じ重さで扱う。記述の誤りは実装の誤りと同じ。
- 移設・改名の後、参照が古いまま残っていないか。
- サンプルコードがそのまま写して安全か。特に DI・認可・スコープの例は、写した結果が本番の初期実装になる。
- 「常に」「必ず」といった強い主張は裏を取る。裏が取れないなら、取れる形にコードを直す。

## 6. 進め方

- **主張は実測する。** 再現コード、実行結果、`grep` の件数を根拠として添える。「〜の可能性がある」は指摘として弱い。
- 深刻度は影響を確認してから決める。fail-safe に倒れることが確認できれば下げる。
- **修正は差分として再評価する。** 修正が新しい規約や新しい結合を持ち込んでいないか、次のレビューで必ず見る。
- 指摘は「何が壊れるか」まで書く。症状が書けない指摘は、優先度を判断できない。

## 7. 機械化しないもの

以下はレビュー時の判断に残します。強制すると偽陽性や形骸化のコストが上回るためです。

- AAA コメントの有無、テスト関数名の書式
- docstring の記述内容の網羅性
- 公開 API の未使用検出（静的には判定できない）
- 命名の適切さ、コメントの粒度
