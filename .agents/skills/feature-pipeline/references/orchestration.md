# 委任・記録の規約

進行役が読む。子へ全文を渡さず、担当者共通規約と役割に必要な情報だけ渡す。

## 起動と続行

- 新規起動は原則`fork_turns="none"`（指定欄がある場合）。元の要件と追加指示、プロジェクト・役割定義・共通規約の絶対パス、3成果物パス、担当範囲、承認対象と版、ケース群・作業単位・方式・モード、品質コマンドを渡す。必要なBASELINE・変更前内容・前段証跡は参照先と関連範囲を指定する。本文と添付文書へ同じ内容を複製しない。
- プロジェクト資料は役割と対象領域で選ぶ。AGENTS.mdの必須条件を省略せず、ファイル・関連節を指定する。子へ全資料の一括読込を要求しない。範囲が広がったら適用資料を追加する。
- 固定の役割指示・共通規約・読込順を安定させる。ケースID・時刻・進捗・ログは固定指示へ埋め込まず、依頼の後半や後続メッセージに置く。
- 統合実装役Generatorを再利用し、テスト作成から実装・検証まで一つの依頼内で進める。Test Writerはパイプラインで起動しない。PlannerとTest Designerへの差し戻しも適合する既存担当を使える。続行は新しいケース群・作業単位・方式・変更点・更新された文書の版・必要な証跡を追記する。過去の会話を毎回再構成しない。
- 履歴の長さだけで頻繁に再起動しない。文脈の混乱、役割の不一致、継続不可、枠不足などの理由があれば必要な状態を渡して新規起動する。環境が提供する終了・待機機能を使い、完了した担当の確認を細かく繰り返さない。
- Evaluatorは実装担当と別にし、原則親の会話を継承しない。前段の結論を正解として渡さず、元の要件・現在の文書・差分・生の証跡を参照させる。別担当であることだけで独立性を保証しない。

## 担当実行中の進行

- 委任時に作業単位、編集範囲、承認版、検証条件、報告先、停止条件をまとめて渡す。担当実行中の追加指示はユーザーの変更、発見した契約上の問題、権限・環境障害、担当からの質問への回答に限る。同じ制約・進捗催促・完了要求を繰り返し送らない。新しい指摘は根拠と影響をまとめて一度に送る。
- 完了通知または待機APIを使い、許容範囲で長めに待つ。親の応答を妨げないよう1回の待機は60秒以内とし、短い待機とsleepを交互に反復しない。定期的なユーザー向け更新のために子へ問い合わせず、既知の進捗を簡潔に伝える。
- 親は承認・範囲・成果物・証跡と未解決箇所を確認する。Generatorが担当中に同じ実装を並行して編集せず、同じテストを進捗確認のためだけに実行しない。子の完了後に証跡不足や懸念があれば対象を絞って確認し、独立した要件照合はEvaluatorへ任せる。
- 検証コマンドには作業ディレクトリ・対象・必要な環境を添える。実行条件の違いで失敗した場合は条件を揃えて切り分け、その原因を直すまで同じ全体ゲートを反復しない。出力取得前の中断や終了コード不明を成功としない。

## 推論量

モデル・権限は呼び出し元を継承する。推論量は共通TOMLで下表を設定し、単独依頼にも適用する。Test Designer・Evaluatorはユーザー指定によりmedium固定、統合実装役Generatorはlow固定とし、自動で変更しない。Plannerはmediumを既定とし、複雑な設計ではhighを明示できる。ユーザーが明示的に設定を変更した場合はその指示を優先する。

| 役割 | 推論量 | 判断 |
|---|---|---|
| Planner | medium（既定） | 曖昧な公開契約・複雑な設計はhigh |
| Test Designer | medium（固定） | 複雑な仕様でも自動で変更しない |
| Generator | low（固定） | Green・Refactor・最終検証も同じ設定 |
| Evaluator | medium（固定） | 必須検証と要件からの評価も同じ設定 |

起動引数の指定欄があれば上表のreasoning_effortを明示する。カスタム役割名を指定できずTOMLの指示を渡す方式でも同じ値を指定する。全文履歴の継承で推論量を指定できない環境ではfork_turns="none"で必要な文脈を渡す。
既存担当の実設定と編集権限・役割指示が上表と統合後の定義に一致すれば再利用する。旧Writer/本番専任Generatorからの移行は現在の作業を終え、差分・証跡・担当解除を確認して統合役を起動する。単なるファイル更新やlow一致だけで旧担当にテスト/本番の両方を許可したと扱わない。不一致の場合は現在の作業の完了と差分・証跡を確認してから、利用可能な終了機能で旧担当を終了し、必要な状態を同じ役割・指定推論量の新規担当へ引き継ぐ。作業中に同じ編集範囲へ別担当を重ねない。成果物・承認・BASELINE・ケース・差し戻し回数を保持する。定義更新だけで起動済みの推論量も変わったと扱わず、確認できない実設定は未確認と報告する。

同一エージェントではモデルと推論量を原則維持し、Red/Green/Refactorのモード変更だけで切り替えない。指定欄や対応する値がなければ継承で進め、その制約を報告する。max/xhigh/ultraへの引上げを自動の既定にしない。

## 進行記録と証跡

PROGRESS_PATHは進行役だけが編集し、次の3部分に分ける。

- **固定情報**: 元の要件、プロジェクト、3パス、BASELINE_STATUSと変更前内容の参照、編集範囲、品質コマンド・作業場所・前提環境。変更が必要なら理由を記録し、元のBASELINEを置換しない。
- **現在状態**: 担当・エージェントID・モデル/推論量（確認できる範囲）、ケース・モード、承認対象と版・会話で得た承認内容、文書/差分の版、変更ファイル、未解決事項・再開条件、評価の差し戻し回数。毎段階・反復後はここを更新する。
- **履歴**: 作業単位・方式、ケースごとの変更前後の結果と必要なRed/Green/Refactorの理由、実テスト位置、検証のコマンド・結果・証跡先、承認・評価・差し戻しを短く追記する。長いログは必要時に隣接する専用フォルダへ保存し参照する。固定情報を毎回複製しない。

版は未コミット差分も識別できるハッシュ・保存差分等で特定する。HEADだけで同一差分と扱わない。現在の証跡が有効か確認し、子の報告だけで承認・完了を記録しない。全コードの重複調査ではなく成果物・差分・証跡と未解決箇所を確認する。

## キャッシュと計測

同じファイル名だけでキャッシュは保証されない。固定指示と既存履歴を安定させ、更新は後続メッセージに置く。キャッシュ率のために不要な文書や履歴を追加しない。キャッシュは推論・生成の削減や品質確認の代わりではない。
使用量が取得できれば親と子・再試行を含め、非キャッシュ入力、キャッシュ入力、出力（推論内訳は二重加算しない）、所要時間、差し戻しを比較する。取得できない使用量は未測定とし、文字数をトークン数と呼ばず、API価格からCodexの利用枠削減率を断定しない。新しい計測のためだけに同じ作業を再実行しない。
