# 薬局ドメインの実装状況

確認日: 2026年9月17日

本書は、この日の作業ツリーを確認した結果のスナップショットです。未コミットの変更も含みます。現在の実装の正典は `app/`、実行可能な保証は `tests/` と `tools/` であり、本書は継続更新する仕様書ではありません。

## 現在の到達点

「患者・保険資格の管理 → 処方箋・疑義照会 → 調剤・鑑査 → 薬歴・頭書き」という中核業務を、ドメインモデル・ユースケース・HTTP API・DB保存まで実装した段階です。

一方、会計や在庫管理、外部システム連携まで含めた薬局業務全体の再現には至っていません。請求業務は実装予定なしとし、今後の実装対象には含めません。12コンテキストがありますが、Claimは資格スナップショットを扱うDomain層のみで、請求ユースケースやHTTPルートはありません。

## 業務ごとの再現範囲

| 領域 | 再現できていること | 境界・不足 |
| --- | --- | --- |
| 法人・店舗 | 法人管理、法人の有効・無効、店舗情報、保険薬局番号、店舗の休止・閉局と管理薬剤師の任命 | 法人・店舗の管理基盤が中心 |
| 本人・アカウント | 本人と個人アカウントの分離、法人内の権限と店舗範囲、本人指定の招待と受諾、操作監査 | 外部の本人確認基盤は未接続。既定の窓口は常に401を返す |
| スタッフ | 資格、主所属・兼務、異動、退職による所属期間の終了 | 所属履歴を扱うモデル。勤怠・給与などは対象にない |
| 患者 | 基本情報、外部患者IDとの対応、外部IDの無効化 | 患者台帳としての基本機能 |
| 保険・公費資格 | 医療保険、公費、有効期間、無効化、期間競合の拒否 | オンライン資格確認との接続はない |
| 受付 | 使用資格の選択履歴、前回選択の取得、適用日での再検証 | 受付全体ではなく資格選択が中心。待ち行列・呼出管理などはない |
| 処方箋 | 薬品・用量・用法、疑義照会、回答、調剤可能への遷移、取消 | 外部の電子処方箋システムとの接続はない |
| 調剤 | 調剤内容、変更調剤、鑑査・監査、完了、リフィル・分割の回数や継続 | 他薬局で実施した回の把握、変更先が本当に後発品かの検証などが不足 |
| 薬歴・頭書き | SOAP、下書き・確定・訂正、残薬・手帳情報、アレルギー・副作用・併用薬等の投影と再構築 | 法定調剤録を代替できる項目充足や保存運用は未検証 |
| 医薬品マスタ | 時点・版付きの薬品情報、剤形、麻薬・後発品区分等の登録と参照 | 薬価基準・HOT等の実データ取り込み、自局採用薬は未実装 |
| 請求 | 医療保険・公費の資格スナップショット | 実装予定なし。点数計算、患者負担計算、レセプト作成・提出・返戻処理は実装対象外 |

全体の境界は[設計概要](../README.md)、請求の実体は[CoverageSnapshot](../../app/domain/claim/coverage_snapshot.py)で確認できます。Claimという名前があることは、請求業務が実装されたことを意味しません。

## 業務の順序と整合性

単に情報を保存するだけでなく、業務の順序や整合性もモデル化しています。

- 未回答の阻害的な疑義照会があれば、処方箋を調剤可能にできない。
- 鑑査を通していない調剤は完了できない。
- 調剤完了時には、終了区分に応じて処方箋の状態も更新する。
- 薬歴確定時には頭書きへ反映する。
- 確定した薬歴の訂正は、元の記載を残して積む。

これらのHTTP経由のシナリオは[臨床業務のAPIテスト](../../tests/presentational/test_http_routes_clinical.py)にあります。調剤と処方箋の一括保存、失敗時の巻き戻しは[DB結合テスト](../../tests/integration/test_complete_dispensing_transaction.py)にも記述されています。

リフィル処方箋と分割調剤については回数・継続を表現していますが、両者の併用可否には原典確認が残っています。機能名が存在することと、制度上のすべての運用を再現できていることは区別が必要です。

## 技術基盤

法人間のアクセス分離、操作権限、PostgreSQL保存、一意性・期間競合の制約、楽観ロック、複数集約のトランザクションを実装しています。

調剤完了と処方箋更新、薬歴確定と頭書き保存は、同じUnit of Workで扱う構成です。関連する処理は[調剤完了ユースケース](../../app/application/dispensing/complete_dispensing.py)と[薬歴確定ユースケース](../../app/application/medication_history/finalize_medication_history.py)にあります。

## 実運用までの主な不足

認証は差し込み口だけがあり、既定実装はすべて認証失敗になります。APIが存在することと、利用者がログインして業務を行えることは区別が必要です。[認証の実装](../../app/presentational/authentication.py)

薬価基準・HOT等の実マスタ取り込みや外部システム接続も残っています。医薬品の規制区分を判定できない場合は、非該当として処理を進めず拒否する設計です。

薬局全体という観点では、会計、在庫・発注・入出庫・棚卸なども未再現の領域です。請求業務は実装予定がなく、残作業には含めません。また、鑑査結果を記録できることは、相互作用などを自動判定する臨床チェックが完成していることを意味しません。

薬歴についても、法定調剤録を代替できるだけの記載事項の検証や、保存期間を保証する運用は未整備です。本書では法令適合性を判定していません。
