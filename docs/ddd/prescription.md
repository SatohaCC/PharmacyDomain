# Prescriptionコンテキスト概要

Prescriptionは、医師・歯科医師が交付した処方箋原本の完全性と、
薬剤師法第24条に基づく疑義照会を管理します。
実際に調剤した内容、調剤鑑査、服薬指導は下流コンテキストの責務です。

## 境界

Prescriptionが所有するもの:

- 受領した処方箋の出所と原本内容
- Rp単位の薬品、用量、用法、リフィル・医師分割指示
- 処方内容に対する疑義照会と回答履歴
- 調剤開始可否と処方箋の終端状態

所有しないもの:

- 患者、店舗、薬剤師の詳細。各コンテキストのIDで参照する
- 実際の調剤結果。Dispensingが1回ごとのセッションとして保持する
- 医薬品マスタの生データ。MedicineCatalogを対象時点で参照する
- 請求時の公費順位。Claimの資格Snapshotとは別の軸である

他コンテキストの存在や資格を調べる処理はApplication Boundaryへ置きます。

## 状態の考え方

処方箋は受付後、処方鑑査を経て調剤可能になります。
調剤終了区分に応じて調剤済となり、取消も終端状態です。

「疑義照会中」は独立した状態にしません。未回答の照会が存在するかどうかから導出します。
状態として持つと、回答後の戻り先を別に覚える必要があり、照会履歴と状態が矛盾できるためです。

## 重要な設計判断

- JAHISと電子処方箋は同じレコード番号を使う箇所があっても、使用可能なコード集合を混ぜず、受領元ごとに検証する
- 疑義照会は調剤編の結果レコードへ送信されるが、内容の対象が処方原本であるためPrescriptionが履歴を所有する
- リフィル指示は医薬品規制区分を交付日時点で確認し、マスタ未収載・判定不能ならfail-closedで拒否する
- 医師の分割指示は処方箋の属性だが、薬局判断の分割はDispensing側の各セッションの理由として扱う
- 処方箋の特殊公費は、数字桁数が固定されたClaimの第四公費へ写さない
- 用量は `Decimal` とし、不均等服用の合計を `float` の誤差で拒否しない
- 引換番号の一意性は受領元ごとの業務判断とし、一律の全体一意性にはしない
- 別表16の薬品補足と変更制限は互いに素な列挙で表し、到達不能な重複検証は置かない

現在の列挙値、入力項目、不変条件の実装は `app/domain/prescription/`、
ユースケースは `app/application/prescription/`、保証範囲は対応テストを確認します。

## 外部根拠の使い分け

| 根拠 | 適用範囲 |
| :--- | :--- |
| JAHIS Ver.1.11 | 紙処方箋の2次元シンボルとコード値 |
| 電子処方箋 処方編Ver.2.4 | 電子処方箋の記録条件と別表 |
| 電子処方箋 調剤編Ver.2.2 | 疑義照会結果など、調剤結果への写像 |
| 保険調剤の理解のために 令和8年度 | 使用期間、リフィル、分割、減数調剤の業務要件 |

規格番号を書くときは規格名と版を併記し、JAHISのレコード番号と電子処方箋の別表番号を混ぜません。

### 薬品コードの原典

処方編・調剤編とも薬品レコードを **`薬品コード X 13 可変`** と定めています。
原典が固定長を定めていないため、固定桁数を不変条件にしません。コード種別ごとの
妥当性は取り込み元のマスタ側の責務とします。

保険者番号や公費負担者番号のように**原典が桁数を定めている**番号は、
これと逆にプリミティブの不変条件として桁数を持たせます。

## 未解決事項

- MedicineCatalog集約はあるが、薬価基準・HOTコード等からの実データ取り込みがない
- 処方箋の公費枠とCoverage台帳を接続する `PublicExpenseAvailabilityBoundary` の実アダプタがない
- 後発品変更調剤で、変更先が本当に後発品かを検証していない
- 本番Repositoryがなく、引換番号一意性の原子性は未証明
- 業務HTTPルートがない

関連する判断履歴は [設計判断](../decisions.md) のADR-1〜3、6、11〜16を参照します。
