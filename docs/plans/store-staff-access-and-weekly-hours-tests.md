# ログイン情報と店舗別の所属・週勤務時間のテスト仕様

作成日: 2026-11-02

状態: 2026-11-02に承認されたテスト仕様。[実装計画](store-staff-access-and-weekly-hours-plan.md)と併せて参照する。
以下は受入条件と検証方針。各項目の実行済み証跡を意味せず、実行結果は末尾に記録する。

## テストの着手順

Domainの不変条件 → Applicationの認可と履歴更新 → PostgreSQL制約・移行 → HTTP契約 → UI操作の順に、失敗を確認してから実装する。
Domainは実オブジェクト、Repositoryの代替は既存のtests/fakesを使う。
テスト名は日本語の `test_<対象>_<条件>_<期待結果>` とし、AAAで整理する。実装内部や文書の番号への依存ではなく利用者から見た結果を検証する。

## 認証と登録

| 条件 | 期待結果 |
| --- | --- |
| 個人メールを省略して初期管理者を登録 | 法人・本人・アカウント・ログインIDが同時に保存される |
| スタッフのログイン資格情報をメールなしで発行 | 発行でき、法人ID・ログインID・初期パスワードで利用開始できる |
| メールが空欄、または有効なメールを指定 | 空欄は未登録、有効値は任意の連絡先として保存される |
| 指定されたメールが不正 | 入力エラーとなり、部分的な登録を残さない |
| 同じメールを複数の本人に設定 | ログインIDが異なれば登録できる |
| 大文字・前後空白を含むID | 定めた正規化後のIDで登録・照合される |
| 同一法人で正規化後IDが重複 | 逐次・同時登録のどちらも重複を保存できない |
| 異なる法人で同じID | 両方発行でき、法人IDを含む照合で混同しない |
| 運営者IDが重複 | 法人利用者とは別の運営者全体の一意性で拒否される |
| IDが2文字・65文字・禁止文字、または有効な3文字・64文字 | 境界どおり拒否・受理される |
| パスワード変更前・期限切れ・試行回数超過・停止中 | 既存の制限、共通エラー、セッション失効が維持される |
| 旧email項目だけをログインAPIへ送信 | 旧契約として拒否し、互換ログインへ回さない |

## 店舗ごとの権限

| 条件 | 期待結果 |
| --- | --- |
| A店編集・B店閲覧の同じスタッフ | A店更新は成功、B店更新は拒否される |
| A店からB店へ店舗選択を変更 | 選択後のActorとSQL読取範囲にA店の編集権限が残らない |
| 法人管理者に店舗編集権限がない | 法人管理は可能だが、店舗業務の編集は自動許可されない |
| 一店舗の利用停止・所属終了・将来の所属開始 | 他店舗への権限を保ち、対象日で利用可能店舗が変わる |
| 有効な管理薬剤師の任命 | 管理対象店舗の既存権限だけが加算される |
| 別店舗の権限・他法人・対象店舗の偽装 | 認可・SQL取得範囲の両方で越境を拒否する |
| ロール変更・店舗停止・任命終了と業務保存が競合 | 同じ法人ロック後の最新状態で判定し、失効後の保存を許可しない |
| 管理薬剤師が他店舗や法人管理権限を変更 | 拒否され、本人の許可された店舗管理範囲に限定される |
| 最後の有効法人管理者の停止・降格 | 既存の保護を維持する |

## 勤務条件と変更履歴

| 条件 | 期待結果 |
| --- | --- |
| A店32時間・B店8時間 | 各所属で別々に保存・取得される |
| 店舗別時間数を変更 | Staff全体の雇用契約上の週所定労働時間を書き換えない |
| 0・0.01・32.5・168時間 | Decimalのまま正確に保存・復元する |
| 負値・168時間超・NaN・無限大・小数第3位 | 明確な入力エラーになり、丸めて受け入れない |
| 未登録と0時間 | 表示・API・DBで区別し、未登録を0として合算・表示しない |
| 指定日から週時間数や従事区分を変更 | 前日までは旧条件、当日から新条件を照会できる |
| 同日開始の条件を訂正 | 訂正前の事実、変更者・記録時刻を追跡できる |
| 所属外の日付・勤務条件の期間重複 | Domainと保存経路で拒否する |
| 所属終了・退職時に将来の勤務条件がある | 既存の所属終了規則と一貫して拒否または明示的に整合させ、孤立した予約を残さない |
| 資格のないスタッフに薬剤師の従事区分を指定 | 操作ロールにかかわらず拒否する |
| 管理薬剤師の任命・終了 | 対象日の業務上の立場が既存任命に従い、独立した真偽値と食い違わない |
| ある店舗の変更前後の一覧 | 対象日の資格者全員を取得でき、別店舗の条件を混在させない |

## 実DBと移行

- 別々のセッションで店舗権限変更と業務保存を競合させ、ロック後の再検証を確認する。
- 勤務条件履歴・所属・監査の更新途中で失敗を注入し、全変更がロールバックされることを確認する。
- 所属期間と履歴期間、本人とスタッフ、法人と店舗の対応を誤らせ、保存できないことを確認する。
- 旧データを入れたmigration前DBで移行し、アカウントID・本人ID・スタッフID・任命・監査が維持されることを確認する。
- 未割当ログインID、正規化後の重複、店舗別時間数の欠落を用意し、前二者は移行拒否、時間数は未登録となることを確認する。
- 法人管理者と一般ユーザーの旧権限を用意し、管理権限と各店舗の操作権限が意図せず増えないことを確認する。
- downgradeを提供する場合は対象データを保全できる条件を検証する。履歴喪失が避けられない場合は黙って破棄せず拒否する。

## HTTP・画面

- メールなしの登録、初回ログインとパスワード変更、通常ログインをブラウザで完走する。
- スタッフ詳細でA店32時間・B店8時間と異なる操作権限を保存し、再読込後も同じ値になることを確認する。
- 適用日を変更して履歴を登録し、現時点と過去時点の表示、同日訂正を確認する。
- 任意メール、業務上の立場、週時間数、システム操作権限を区別して表示し、未登録を明示する。
- 無権限時の編集不可、保存失敗時の入力保持、重複送信防止、狭い画面とキーボード操作を確認する。
- Storybookにメールなし・複数店舗・時間数未登録・勤務条件履歴・閲覧のみ・保存失敗を用意する。

## 品質ゲートと証跡

AGENTS.mdに記載されたバックエンド・フロントエンドの標準ゲートと、専用PostgreSQL DBの結合テストを実行する。
OpenAPI生成後の型、Ruff、mypy strict、import・Domain/Application境界検査も確認する。
DBスキップやブラウザ未実施は成功に含めず、実行コマンド・件数・失敗と再実行範囲を分けて報告する。
