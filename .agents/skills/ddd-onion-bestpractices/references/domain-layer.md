# Domain

## 責務と概念

Domainは業務語彙・判断・状態の整合性を所有する。Web/ORM/DB Session/外部SDK/Applicationへ依存しない。本Skillの厳格なPython既定では標準ライブラリだけを使う。FW非依存という原則と、特定プロジェクトが採用するライブラリ制限は区別する。

| 概念 | 選ぶ基準 |
|---|---|
| Domain Primitive | 単一値の意味・値域・必要な正規化を所有する小さなVO |
| Value Object | IDではなく値で比較する。単一値でも複数値でもよく、原則不変 |
| Entity | IDで同一性を追い、業務上のライフサイクルを持つ。等価性と状態比較を区別する |
| Aggregate | 同時に守る不変条件の境界。Rootが整合性を維持する。テーブル/コレクションの別名ではない |
| Domain Service | Entity/VOに自然に属さない業務判断。モデル内の操作をサービスへ追い出さない |
| Repository抽象 | 集約の保存/取得に必要な契約。ORM/Session/HTTPカーソルを露出しない |
| Domain Exception/Event | 業務上の失敗/発生した事実。HTTP/配送/ログ実装を含めない |

Entityを不変オブジェクトの置換で実装してもよい。状態変更の方法より、Rootを通じて不変条件が常に守られることを確認する。公開コンストラクタで子VOを作れることと、集約の内部状態を外から無制限に変更できることを混同しない。

一時的な照合・重複排除・検索グループは、固有の同一性・ライフサイクル・整合性境界がなければEntityにしない。非公開の作業状態と不変の結果VOで足りるか判断する。

## 値の検証と文脈の検証

- Primitiveはその値自体の規則を一度検証する。VO/EntityはそのPrimitiveを受け取り、**利用文脈の制約**や値の関係を検証する。これは重複した型検証ではない。
- 例: Quantityが0以上を許しても、受注明細では0を許さないならLineが正数を要求する。日付が有効でも期間の開始/終了関係はVOが検証する。
- AggregateはID重複、親の存在、集合全体の整合性、許可された状態遷移を守る。階層番号から親を導出できても、親の存在検査は必要。
- 遷移失敗で一部の状態だけが変わらないよう、検証後に変更するか不変の新状態を返す。ロールバックがインメモリオブジェクトも元に戻すとは仮定しない。
- 正常な生成とDB/XML等からの復元に同じ不変条件を適用する。検証を迂回する復元や、外部DTOが検証済みという理由での業務検証省略はしない。

Pythonでは型注釈を外部入力の実行時検証と扱わない。外側で検証してPrimitive/VO/tuple/frozensetへ明示変換する。内部では型検査を使い、全フィールド/全要素のisinstance、型確認だけの_require/_require_items、単一値の再検証を追加しない。内部型契約をAny/castで破る拒否テストを、要件なしに増やさない。

## 生成・復元・不変性

- Entity/VOは型付け済みの値を直接コンストラクタへ渡す。__post_init__は業務上の文脈制約・組み合わせ・集約の検証に使い、str/list等を暗黙変換する場所にしない。
- 変換だけのcreate()や別名生成APIは作らない。複雑な構築方針・外部ID発行等の独立した責務が本当に必要なら、その所有者と契約を定める。既存の単純ラッパー削除で不変条件を消さない。
- Primitiveのparse/from_valueや、外部SDK/ORMのcreateは、この変換だけのモデルラッパーと区別する。
- コレクションは型付け済みの不変値として渡す。frozenでも内部listの変更は防げない。必要な防御的コピーはその所有者で行い、全モデルへ暗黙変換を分散させない。
- 原文・スナップショットには汎用BaseStringのtrim/NFKCを機械適用しない。空本文が有効ならそのまま保持し、不在Noneと区別する。名前/ID等の非空規則とは別の契約にする。外へは.value等で明示的に取り出す。
- 独立した複数の値は不変集合で表し、全組み合わせをEnumで列挙しない。順序が意味を持つならtuple等を選ぶ。公開配列の順序、空集合と未取得/不明の違いを定める。
- 一意に導出できる値は二重入力にしない。基準時刻・乱数は明示値や小さなPortを介し、モデルが現在時刻/外部クライアントを勝手に取得しない。

## コンテキストと所有権

境界づけられたコンテキストは語彙とモデルの意味の境界で、フォルダ名だけでは決まらない。既存のモデル・変更責任・連携契約から判断し、新しい共有領域やコンテキスト分割は根拠がある場合に限る。

- IDの正本は識別対象の所有元。複数箇所で使うだけでsharedへ移さない。Shared Kernelは意味・制約・変更責任を共同管理する合意がある語彙に限り、業務コンテキストへ逆依存させない。
- 厳格な公開ID方式では他コンテキストから直接参照できるのは所有元のidentifiers.pyだけ。Entity/VO/Exception/内部Serviceを再公開しない。必要な情報はApplicationが利用側のモデルへ変換する。他方式を採用済みのプロジェクトでは、その明示的な契約を確認する。
- 原本の構造・改訂・整合性は原本側、検索単位・取得結果の統合は利用側が所有する。利用側は原本IDと必要なスナップショットを持つ。別モデルを残す根拠は用途・不変条件・ライフサイクルの違い。索引保存/SQLはInfrastructure、変換の調整はApplication/取り込みユースケース。
- 集約間はIDや参照用の値で関連づけ、他集約の可変な内部状態を直接操作しない。強い整合性が本当に必要な範囲を決め、複数ストアを一つのAggregateと呼んで原子性を仮定しない。

## 厳格なPython配置プロファイル

対象がこの方式を採用する場合に使う。既存の言語/配置を置換したり、空ファイルを揃える目的には使わない。

```text
domain/
  foundation/              # 業務非依存の基底
  shared/                  # 合意した共有語彙
  <context>/
    identifiers.py         # 公開するEntity ID
    exceptions.py
    primitives.py
    value_objects.py
    entities.py            # Entity/Aggregate Root
    repositories.py
    services.py
```

- 標準の内部依存は identifiers/exceptions ← primitives ← value_objects ← entities ← repositories ← services。IDと例外の相互依存等の細部は対象の静的契約で確認する。必要のない階層を増やさない。
- identifiers.pyは標準ライブラリと合意したID基底モジュールだけを参照し、通常Primitive/shared/他コンテキスト/内部モデルを参照しない。ID基底モジュール自身に利用側の制限を再帰適用しない。
- この命名方式では型名を〜Id、属性名を〜_id/〜_idsへ統一。同じIDにKey/Idの別名や旧パス再公開を残さない。外部保存形式の維持が必要なら外側で変換する。互換性の要否は対象プロジェクトの方針に従う。
- 巨大化したファイルは集約/コンテキストの責務を先に見直す。分割・移動時は利用側と検査を更新し、禁止依存をFacadeで隠さない。

## 業務ポリシーと検証

認証情報の解釈・入口のアクセス認可は外側/Application。資格・契約・状態に基づく「この業務操作を実施できるか」はDomainの業務ポリシーになり得る。ユーザーroleをHTTPから持ち込む代わりに、必要な業務上の事実を渡す。

純粋なDomain判断には取得済みのモデル/事実を渡す。Repository等のI/Oが必要な場合、抽象がDomain所有でも純粋関数とは呼ばない。取得・確定との調整はApplicationに置き、現在状態が重要なら[UoW](unit-of-work.md)で競合時の再検証を設計する。

テストは実モデルを使い、Primitive値域、文脈制約、生成/復元、遷移成功/失敗後の状態、集約全体の整合性を分けて観測する。外部PortにはFakeを使えるが、構造検査だけで不変条件が検証できたとは扱わない。

原典: [Fowler Aggregate](https://martinfowler.com/bliki/DDD_Aggregate.html)、[Value Object](https://martinfowler.com/bliki/ValueObject.html)。具体的なPython配置と公開ID方式は本Skillのプロファイルであり、原典に共通する必須ファイル規約ではない。
