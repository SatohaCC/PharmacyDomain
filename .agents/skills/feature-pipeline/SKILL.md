# Feature Pipeline

`$feature-pipeline <要件>` または `/feature-pipeline <要件>` で開始する。Planner・Test Designer・Generator（テストと本番の統合実装役）・Evaluatorの4役で進める。
進行順は計画書承認 → テストケース（テスト仕様）承認 → テスト先行または変更前後の回帰検証 → 評価 → 完了報告。
ユーザー承認の対象は計画書とテストケースの2つだけ。承認後は承認済み範囲の実装・検証・評価・修正・再評価まで進め、実装や評価結果への追加承認は求めない。
単独の役割の依頼ではその範囲だけを行い、全パイプラインを開始しない。

## 呼び出し条件

ユーザーが`$feature-pipeline <要件>`、`/feature-pipeline <要件>`、または「feature-pipelineを使ってこの作業を開始/再開して」と実行を明示した場合だけ開始する。通常の機能追加・バグ修正・計画・テスト依頼では自動適用しない。
Skill名・リンク・本文の添付だけでは実行指示と扱わない。Skillやエージェント定義の説明・レビュー・編集依頼はその依頼だけを処理し、パイプラインを起動しない。
明示的に開始した同じ作業の承認・修正・続行では再指定を要求しない。ただし、別の作業へ自動的に適用を引き継がない。進行役の資料選択やAGENTS.mdからの参照も、ユーザーの実行指示の代わりにしない。
`agents/openai.yaml`の`policy.allow_implicit_invocation: false`を維持する。

## 開始・再開

進行役は開始時に[委任・記録の規約](references/orchestration.md)を読む。子には自身の役割定義と[担当者共通規約](references/agent-contract.md)を渡し、このSkill全体は読ませない。

- ユーザーが指定したプロジェクトの現在の作業ツリーを使う。適用されるAGENTS.mdと、その読み分けに従う資料を確認する。不足は既存コード・テスト・README・CI・パッケージ設定から調べ、別プロジェクトの規則を持ち込まない。
- 本番・テスト・Fixture・Fakeの編集範囲、品質コマンドと実行場所、必要な環境・サービスを特定する。同居するファイルも役割で分ける。
- `git status --short`をBASELINE_STATUSとして記録する。変更予定箇所の既存差分・未追跡内容を保存または参照可能にし、一覧だけで帰属を判断しない。Git管理外は変更前の内容を記録し、Gitを初期化しない。
- 日付・topicと次の3パスを固定する。ユーザー指定の保存先を優先し、同名の既存成果物を上書きしない。

| 変数 | 既定パス |
|---|---|
| PLAN_PATH | `for-llm/plan/YYYYMMDD-<topic>.md` |
| TESTCASE_PATH | `for-llm/testcase/YYYYMMDD-<topic>.md` |
| PROGRESS_PATH | `for-llm/progress/YYYYMMDD-<topic>.md` |

再開はPROGRESS_PATHと現在の差分を照合して記録された段階から続ける。日付・パス・BASELINE・差し戻し回数をリセットせず、有効な承認を取り直さない。確認できない承認は推測しない。旧手順の`USER_REVIEW_REQUIRED`から再開する場合は、有効な計画・テストケース承認と現在の差分への評価・必須検証を確認して完了報告へ進む。評価・証跡が不足または古ければ必要な検証・評価を行い、旧手順の実装承認は要求しない。

## 役割と委任

| 起動名 | 定義 | 編集範囲 |
|---|---|---|
| `planner` | [Planner](../../agents/planner.md) | PLAN_PATH |
| `test-designer` | [Test Designer](../../agents/test-designer.md) | TESTCASE_PATHの仕様 |
| `generator` | [Generator](../../agents/generator.md) | 計画に含まれるテスト・Fixture・Fake・本番側、ケースと実テストの対応欄 |
| `evaluator` | [Evaluator](../../agents/evaluator.md) | ソース編集なし、評価と必要な検証 |

担当段階の定義を読み、対応する共通エージェントへ委任する。カスタム起動名を指定できなければMarkdown役割定義の「役割指示」を起動プロンプトとして渡す。起動・再利用・推論量は委任規約に従う。
同じ作業ツリーで書き込み段階を同時実行しない。結果・実際の差分・証跡を確認して次へ進む。子は次の役割を起動しない。
Evaluatorは実装担当と別のエージェントにする。元の要件、承認済み成果物、BASELINEと差分、実際の証跡を渡し、実装担当の自己評価を結論として渡さない。
サブエージェントが使えない、または単独実行の指定がある場合は同じ定義で進行役が切り替え、その方式を報告する。

## 段階

### 1. 計画

Plannerへ元の要件に対応する目的・範囲・公開契約・受入条件・検証方法を依頼する。計画と要約を提示し、実際の計画承認を待ってTest Designerへ進む。

### 2. テスト仕様

Test Designerへ要件とケースの対応、前提・操作・期待結果、既存テストの再利用、必要な検証層、着手順と、関連ケースをまとめる作業単位・小単位TDDが必要な箇所を依頼する。ケース漏れを確認して仕様を提示し、実際の仕様承認を待つ。計画変更はPlannerへ戻す。

### 3. 作業に応じた実装・検証

進行役は計画・承認済み仕様に沿って作業単位と方式を選び、対象ケースID・理由を記録する。

| 作業 | 方式 |
|---|---|
| バグ修正・重要な業務ルール | 小単位のTDD。Generatorがテストの再現・期待する失敗を確認してから本番実装する |
| 通常の機能追加 | 関連ケースをまとめてテスト先行。Generatorが関連ケース群を書いて変更前の結果を記録し、そのまま本番実装へ進む |
| 振る舞いを保つ構造整理・移動 | 既存テストで変更前後を確認。新規Redは必須にしない。既存カバレッジが不足する場合はGeneratorが必要な回帰テストを先に追加する |

1. 依存関係・共有API・影響範囲を基に、独立して検証できる作業単位を選ぶ。一律の件数や全ケース一括を強制せず、小さな機能なら全関連ケースを一単位としてよい。重要な業務ルールを通常機能のまとめ処理に埋め込まない。
2. Generatorへ方式・ケース群・期待結果とテスト/本番の編集範囲を一度に渡す。新規API不足なら同じ担当が承認済みAPIの最小スタブだけを追加してテストへ戻る。バグ・重要ルールは期待したアサーション失敗または明示的な未実装エラーを必須とする。通常機能もテストを先に実行し、各ケースの期待した失敗・既存Green・未実行を区別する。構文・import・ビルド・環境エラーはRedではない。
3. Generatorは変更前の結果を記録してから、同じ依頼内で指定範囲の本番実装・テストと本番のRefactor・対象と関連既存/完了済みケースの検証まで行う。テスト作成と実装の間で進行役への往復を必須にしない。承認済み期待結果や検証範囲を変えて通さず、仕様変更はTest Designerへ戻す。構造整理は有効な変更前Greenを確認してから着手し、変更後もGreenを確認する。変更前の失敗は原因を記録し、今回の退行と区別する。必要な検証を実行できない場合は未完了として扱う。
4. テスト側の不備修正・Refactorも仕様の意味を保つ範囲でGeneratorが行う。進行役は作業単位の成果物・差分・証跡をまとめて確認し、ケースごとの結果と実テスト位置を保持して次へ進む。まとめた報告のためだけにケースごとの往復を挟まない。

方式・作業単位だけの変更で要件や仕様の意味が変わらなければ再承認は不要。途中再開でも完了済みケース・有効な証跡・承認を保持し、現作業を終えてから残りへ適用する。仕様変更には通常の再承認規則を適用する。

全ケース後、Generatorへ必須品質ゲートと計画固有の最終検証を依頼する。反復中は関連テストを使い、全ゲートを毎回繰り返さない。現在の差分に有効な証跡は利用できる。
全ケースと必須検証が完了した場合だけ`GENERATOR_COMPLETE / EVALUATION_REQUIRED`としてEvaluatorへ進む。必須検証ができなければ未完了とし、原因と再開条件を記録する。追加のユーザー承認は求めない。

### 4. 評価と完了報告

計画・仕様の承認、Generatorの完了、現在の差分を確認し、追加のユーザー承認を挟まずEvaluatorへ依頼する。要件→ケースの漏れとケース→テスト・実装の対応を確認させる。
現在の差分に有効な証跡は再利用し、不足・変更後の未実行・指摘に関わる懸念があれば必要な検証を行う。テスト、実DB、型・lint・ビルド、ブラウザ、CI等の層を区別する。未実施・skip・xfailは成功に含めない。

## 変更前の失敗と品質ゲート

変更前に失敗があれば、ケース・原因・実行条件・影響する契約を記録する。「既存」という理由だけで必須ゲートから除外しない。承認済み計画・仕様で対象外の既存失敗を許容する条件が定められている場合に限り、同条件の変更前後比較で悪化がなく、今回の受入条件をすべて満たすことを確認して範囲内の評価へ進める。全体成功とは報告しない。
必須ゲートが全体成功を要求している、除外条件が未承認、または今回変更する契約に失敗が関係する場合は未完了として扱う。必要な修正または検証条件の変更を計画・仕様へ戻し、実際の再承認を待つ。Evaluatorも許容条件の承認と前後比較を確認し、失敗件数が同じだけで退行なしと判断しない。

## 変更と差し戻し

- 要件・範囲・公開契約・受入条件の変更はPlannerへ戻し、計画を再承認する。影響する仕様もTest Designerで見直す。
- 検証する入力・前提・操作・期待結果・検証範囲の追加・変更・削除やケース漏れはTest Designerへ戻し、仕様を再承認してから実装する。
- 意味と検証範囲を保つ命名・重複整理・Fixture/Fakeの不備修正・非公開の実装整理は担当役割で進め、理由・対応ケース・再検証を記録する。Fixture/Fakeでも条件が変わるなら仕様変更。期待値緩和・ケース削除・skip追加を整理として通さない。不明なら担当設計役へ確認する。
- 評価後のコード・テスト変更は影響を再評価する。古い差分への判定を流用しない。

| 判定 | 進行役の処理 |
|---|---|
| PASS | 要件・受入条件・ケース・必須検証を満たした場合のみ。評価、最終差分、検証した層、未確認事項と残余リスクを提示し`PIPELINE_COMPLETE`を記録して作業ツリーに残す。実装・評価結果の承認待ちは設けない |
| NEEDS_REVISION | 本番・テストの修正はGenerator、ケース漏れはTest Designer、要件・設計はPlannerへ戻す。必要な再承認と修正・検証後に再評価。環境不足も未完了として再開条件を示す |
| FAIL | 設計や前提が成立しない場合は停止し、理由と判断事項を示す |

評価からの自動修正・再評価は全体で最大2回。通常の実装・検証の反復は含めない。回数を記録して再開でも保持し、上限では未解決事項を残して停止する。新しいユーザー指示なしに続けない。
計画書・テストケースの承認は会話で得たものだけを扱う。一般的な着手指示、テスト成功、PASSをそれらの承認と読み替えない。ユーザーが承認手順を明示変更した場合は記録して従う。
ブランチ・Worktree・コミット・PRは明示依頼がある場合のみ。reset・stash・cleanによる自動退避・破棄はしない。
