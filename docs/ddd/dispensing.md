# Dispensingコンテキスト概要

Dispensingは、処方箋に基づいて自局で行う1回ごとの調剤作業、変更調剤、
調剤薬剤師と鑑査薬剤師の記録、最終鑑査を管理します。
処方原本はPrescription、服薬指導はMedicationHistory、報酬算定はClaimの責務です。

## 境界

1枚の処方箋に対して、リフィルや分割調剤により複数の調剤セッションが発生します。
各 `DispensingProcess` は1回の実施事実だけを表し、同じ処方箋と回次の重複を許しません。

### 自局実施分の境界

本コンテキストが保持するのは自局実施分だけです。患者が別の薬局で次回調剤を受けた場合、
その回は自局の集約にならないため、自局の件数と処方箋全体の総回数は一致しないことがあります。

したがって、保持している調剤セッションの**件数から調剤回数を導出してはいけません**。
回次は各セッションが自分で持ちます。

Dispensingの集約自体はPrescription集約を保持しません。
原本との整合性のように複数集約が必要な判定はDomain Service、
薬剤師資格などの外部参照はApplication Boundaryが担います。

## 変更調剤

変更調剤は1つの列挙へ潰さず、独立した3軸で表します。

| 軸 | 意味 |
| :--- | :--- |
| 代替調剤 | 銘柄や後発品への置換 |
| 数量調整 | 減数など数量の変更理由 |
| 調製方法 | 一包化、粉砕などの調製上の変更 |

電子処方箋の調剤結果情報には、変更調剤を直接表す共通コード体系がありません。
送信時は実際に調剤した薬品を記録し、原本との差分と本ドメインの変更理由を別に扱います。

## 加算はClaimの責務

一包化、無菌製剤処理、麻薬・向精神薬の取扱いなどは調剤の**事実**として記録しますが、
それが加算になるか、加算どうしが排他かはClaimが決めます。
ここへ請求規則を混ぜると、報酬改定のたびに調剤の記録が変わることになります。

## 重要な設計判断

- リフィル、医師分割、長期保存困難等による分割、後発品試用の分割を同じ回数規則へまとめない
- 変更前後が同一の代替調剤は、監査上意味のない変更記録になるため拒否する
- 調剤と鑑査の担当者は、集約間参照を避けてIDで保持し、資格はBoundaryから得た情報で確認する
- 中止理由は捨てず、取消状態と理由の有無を一致させる
- 調剤終了は単なる総回数到達ではなく、調剤結果の終了区分を根拠に処方箋へ反映する
- 技術料・加算の算定可否はClaimへ委ね、Dispensingに請求規則を混ぜない

現在の状態、回次数、変更理由、検証条件は `app/domain/dispensing/`、
ユースケースは `app/application/dispensing/`、保証範囲は対応テストを確認します。

## 外部根拠

- 薬剤師法は調剤できる者、処方箋による調剤、情報提供、調剤済処方箋への記録を定める
- 「保険調剤の理解のために」はリフィル、分割、減数調剤の業務条件を定める。
  調剤日の許容範囲は同書 §3-1 通則に原文があり、原典で確認済み

> ２回目以降の調剤については、原則として、前回の調剤日を起点とし、当該調剤に係る
> 投薬期間を経過する日を次回調剤予定日（実際に投薬が終了する日）とし、
> **その前後７日以内**とする。

同じ箇所が減数調剤を「用法及び用量の変更は行わずに投与日数等を減らす調剤」と定義しています。
この定義に従い、用法・用量を変えず数量だけを減らすものとして扱います。
- 電子処方箋の調剤編は調剤結果、疑義照会結果、リフィル終了情報の送信形式を定める

## 未解決事項

- リフィル処方箋と分割調剤の併用可否を原典で確認できていない。「保険調剤の理解のために」は
  両者を並列に挙げるだけで、同一処方箋での併用については述べていない
- 調剤セッション保存とPrescriptionの調剤済遷移が同一トランザクションではない
- 他薬局で実施した回を把握するモデルがない
- 本番Repositoryと業務HTTPルートがない

関連する判断履歴は [設計判断](../decisions.md) のADR-5〜7、11、13を参照します。
