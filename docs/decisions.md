# PharmacyDomain 設計判断

プロジェクトの重要な設計判断と、その採用理由・却下理由を時系列で残します。
現在の型と振る舞いはコード、保証範囲はテストと静的チェッカを正とします。

## 2026-09-24

### ADR-59: package initializerから再エクスポートせず、定義元moduleを直接importする

- **背景**: `__init__.py` が型や集約を先読みすると、プリミティブだけをimportした経路でも隣接コンテキストのRepositoryや集約が初期化され、cold-start時に循環importが起きる。先行テストのimport順によって循環が隠れるため、通常のpytest成功だけでは検出しにくい。
- **決定**: `app/`・`tests/`・`tools/`・`migrations/` の全 `__init__.py` は空またはモジュールドキュメント文字列だけにする。公開名は再エクスポートせず、利用側は定義元moduleから直接importする。循環importは `tools/check_imports.py` がASTから構築したmodule graphへ `graphlib.TopologicalSorter` を適用して検出し、既存のarchitecture品質ゲートで失敗させる。
- **理由**: package initializerに実行文を置かなければ、パッケージ名だけのimportが子モジュール群を暗黙に読み込む経路を作らない。利用側から定義元までの依存がimport文に現れ、単一の標準ライブラリ解析で循環を検出できる。循環検出と個別のcold-start入口テストを既存ゲートへ接続し、CI jobを増やさない。
- **適用**: 新しいクラス・関数・Protocolは通常moduleで定義し、`__init__.py` の `__all__` へ登録しない。`UnitOfWork` と `PostgresRepositorySet` も専用moduleからimportする。
- **限界**: 静的graphは構文上のimportを対象とし、`importlib` 等で組み立てる動的importは列挙しない。通常の依存は直接importで表し、重要な実行入口は別processのcold-startテストで確認する。

## 2026-09-21

### ADR-58: 電子薬歴を中心とするコアドメインの確立と、レセコン（請求・会計・算定判定）との責務境界の確定

- **種別**: アーキテクチャ境界確定 / ドメイン分析 / スコープ整理
- **背景**:
  本リポジトリの開発進捗およびIssueの検討過程において、以下の3つの典型的な「レセコン（請求・会計・算定システム）の責務」が調剤・薬歴ドメインへ混入・越境しようとするリスクが顕在化した。
  1. **Issue #6（分割調剤の回数算定バリデーション）**:
     調剤基本料注9の点数算定ルールが集約の不変条件として混入し、第1回目の長期保存困難分割調剤が拒否された（ADR-57で是正）。
  2. **Issue #7（調製方法の結合関係モデリング）**:
     計量混合調剤加算（同一剤・異剤混合）や一包化加算のレセプト算定を見据え、複数薬品を束ねる結合・容器モデル（`PackagingGroup` 等）の導入が提案された。
  3. **Issue #11（公費負担医療における上限額管理票モデリング）**:
     指定難病等の自己負担上限額管理票（月額上限額、当月累積額計算、窓口負担金計算）のモデリングが提案された。

  調剤薬局の実務において、店舗業務は大きく**「レセコン（医事会計・レセプト請求システム）」**と**「電子薬歴・調剤システム（本ドメインのコア）」**の2つの独立したシステム領域に二分される。
  レセコンの責務（2年ごとの診療報酬改定に追従する点数算定、自己負担金計算、公費上限額管理、レセプト作成）を電子薬歴システムが内包しようとすると、ドメインモデルが過剰に肥大化し、本来の臨床・服薬指導の整合性境界が破壊される。
- **決定事項**:
  1. **電子薬歴システムを中心とするコアドメインの確定**:
     本システムのコアドメインを**「電子薬歴（MedicationHistory）および付随する臨床調剤事実記録（Dispensing）、処方箋原本・疑義照会管理（Prescription）、患者医療プロファイル投影（Patient）」**と明確に定義した。
     薬剤師法第25条の2（情報提供及び指導）、第28条（調剤録）、薬剤師倫理に基づく薬学的管理指導を最上位の関心事とする。
  2. **レセコン責務の完全除外（Issue #7, #11のクローズ）**:
     以下の業務領域はレセコンの排他的な責務であり、本ドメインには持ち込まない。
     - **調剤報酬点数・各種加算の算定判定**: 計量混合調剤加算、一包化加算、調剤基本料注等の算定可否判定はレセコンの責務である。本システムは `DispensedMedicine.preparations`（調製方法フラグ）として客観的調剤事実を保持するにとどめ、複雑な結合構造（Issue #7）は導入しない。
     - **金銭会計・保険自己負担金計算**: 窓口での一部負担金計算や公費の月額自己負担上限額の累積計算・管理票記帳（Issue #11）はレセコンの責務である。
     - **レセプト（診療報酬明細書）作成・請求**: 審査支払機関へのオンライン請求業務はレセコンの責務である。
  3. **外部連携インターフェース（NSIPS等）による客観的事実の受容**:
     レセコンからNSIPS（新調剤システム情報交換仕様）等を介して連携されるデータ（処方、調剤回数、合計分割回数、分割理由、調製区分等）は、外部で確定した「客観的な業務事実（Fact）」として受け入れ、ドメイン内で算定要件の追試・先回り検証を行わない。
  4. **調剤機器（分包機等）との役割分担**:
     薬品をどの包・容器に充填するかという物理的指示・印字データの生成は、レセコンからNSIPS処方データを受け取る調剤機器（分包機・水剤分注器）側の責務とする。薬歴側は指導上の必要な説明事実をSOAPやメモ（`additional_notes`）に自然言語で記録すれば十分とする。

### ADR-57: 分割調剤の回数算定バリデーションをDispensing集約から撤廃し、NSIPS連携データに基づく自己無撞着性管理へ是正する

- **種別**: ドメインモデル改定 / 責務境界是正
- **背景**:
  `DispensingProcess`（調剤集約）に調剤基本料注9・10・11の点数算定要件（`_SPLIT_ITERATION_RANGES` および `_ensure_iteration_matches_split_reason()`）が不変条件として混入し、長期保存困難（注9）の分割調剤において第1回目の調剤セッションが `DispensingIterationOutOfRangeError` で不当に拒否される不具合（Issue #6）が発生していた。
  薬局実務において、分割調剤の可否判定・回数管理・点数算定はすべてレセコン（受付・会計・請求システム）の責務である。本システム（調剤・薬歴ドメイン）は、レセコンからNSIPS（新調剤システム情報交換仕様）等を介して受け取った調剤セッション事実（分割理由 `split_reason`、今回調剤回数 `iteration`、合計分割回数 `total_split_count`）を客観的に記録する責務を持ち、集約単体で算定要件を先回りして回数を裁くべきではない（ADR-49の「受付NSIPS単位で記録を完結させる」原則）。
- **決定事項**:
  1. **算定要件バリデーションの完全撤廃（方針A）**:
     `DispensingProcess` 集約から算定ルールに基づく回数制限バリデーション（`_SPLIT_ITERATION_RANGES`、`_ensure_iteration_matches_split_reason()`）を完全に撤廃した。これにより、長期保存困難（注9）の第1回目を含め、レセコンから連携された正当な業務事実を客観的に記録可能とした。
  2. **NSIPS受信データとしての合計分割回数（`TotalSplitCount`）の導入**:
     レセコンからNSIPS連携される分割調剤データ構造（今回回数・合計分割回数・分割理由）に基づき、`TotalSplitCount(BasePositiveInt)`（2以上の正の整数）を導入した。
  3. **セッション単独の自己無撞着性（集約不変条件）**:
     集約では点数算定要件には立ち入らず、セッション単独の自己無撞着性のみを保証する。
     - `split_reason` と `total_split_count` は双方が指定されているか、双方が未指定（通常調剤）であること（片方のみは `TotalSplitCountMismatchError` で拒否）。
     - 分割調剤時、今回回数は合計分割回数以下であること（`iteration.value <= total_split_count.value`、超過時は `DispensingIterationOutOfRangeError` で拒否）。
  4. **処方箋原本との臨床的整合性（Domain Service）**:
     医師指示による分割調剤（`PRESCRIBER_INSTRUCTED`）については、`DispensingPrescriptionConsistencyService` において処方箋原本の分割指示（`management.split`）との突合（処方箋に指示があること、および調剤回数・合計分割回数が処方箋指示の全分割回数以内であること）を引き続き検証し、臨床安全性を担保する。
  5. **永続化の後方互換性**:
     `DispensingProcess` の `total_split_count: TotalSplitCount | None = None` は既定値を持つため、既存の PostgreSQL `dispensing_processes.payload` JSONB レコードの復元を壊さず、マイグレーション不要で完全な後方互換性を維持する。

### ADR-56: 患者集約のライフサイクル（有効・無効・名寄せ統合）と非破壊的マージのモデリング

重複登録された患者の統合（名寄せ）や、死亡・転居・利用停止に伴う無効化の要求に対し、
過去の処方箋原本・調剤セッション・薬歴記録との不可分性を保ちつつ、安全に患者集約の
状態を遷移させるモデリング方針を決定した。

患者データは処方箋（`Prescription`）・調剤（`DispensingProcess`）・薬歴（`MedicationHistoryRecord`）
などの法的文書から外部キー（`PatientId`）で参照されている。重複患者を物理削除したり、
過去データの外部キーをマージ先端のIDへ機械的に一括書き換えする「破壊的マージ」は、
過去の調剤時点における保険資格確認・服薬指導の真正性を損なう重大なリスクがある。

したがって、以下の設計判断を採用した。

1. **ライフサイクル方言を `status_enum` とし、監査履歴を保持する**:
   患者（`Patient`）のライフサイクル方言を従来の `none`（状態なし）から `status_enum` へ改定した。
   状態は `PatientStatus.ACTIVE`（通常有効）、`INACTIVE`（利用停止・無効）、`MERGED`（他患者へ統合済み）
   の3値とし、状態変更監査ログ `status_history: tuple[PatientStatusChange, ...]` にて
   変更日時（タイムゾーン必須）・変更前状態・変更後状態・変更理由（`PatientStatusReason`、
   空文字禁止・200文字制限）・統合先IDを不変タプルとして追記保持する。
2. **非破壊的マージ（統合元集約の凍結）の採用**:
   マージ操作では、統合元（source）のステータスを `MERGED` へ遷移させ、`merged_into_id` に
   統合先（target）の `PatientId` を記録して凍結する。
   過去の調剤・薬歴データの参照先IDは改変せず、当時の事実をそのまま残す。
   統合元が特定された業務照会においては、`merged_into_id` を参照して現在の真実へ誘導できる。
3. **終端状態としての保護と属性変更のブロック**:
   `MERGED` は終端状態であり、統合済み患者に対する再度の名寄せ（多段マージの防止）、
   再有効化（`reactivate`）、無効化（`deactivate`）を `PatientStateConflictError` で拒否する。
   さらに、統合済み患者に対する氏名変更（`change_names`）や生年月日変更（`change_birth_date`）も
   `PatientStateConflictError` で拒否し、凍結された過去の患者情報の改変を封じる。
4. **ドメインサービス（`PatientMergeService`）による複数集約整合性と多重防御**:
   マージは2つの患者集約にまたがるため、無状態の `PatientMergeService.merge()` が担当する。
   - **マルチテナント境界**: `source.corporate_id == target.corporate_id` を検証し、法人間マージを拒否（`PatientMergeCorporateMismatchError`）。
   - **自己マージ禁止**: `source.id != target.id` を検証し、自身への統合を拒否（`PatientSelfMergeError`）。集約不変条件でも `merged_into_id != id` を二重に強制する。
   - **統合先端の有効性**: `target.is_active is True`（target が `ACTIVE` であること）を要求し、無効化済みまたは統合済みの患者を宛先とするマージを拒否。
5. **JSONB永続化の透過性と後方互換性**:
   `Patient` 集約のフィールド追加（`status=ACTIVE`, `merged_into_id=None`, `status_history=()`）は
   dataclass の既定値で宣言されているため、既存の PostgreSQL `patients.payload` JSONB レコードに対し
   DBスキーマの `ALTER TABLE` やマイグレーションを一切不要とし、完全な後方互換性を維持する。

### ADR-46: 本人確認境界の出力は、外部主体だけにする

本人確認境界は `VerifiedIdentity`（内部の本人ID + 外部主体）を返していた。**外部の
認証基盤は自分が発行した `sub` しか知らず、このシステムの本人IDを知らない。** そのため
この形では本物のIdPアダプタを書けず、実装は「必ず失敗する既定」とテストのダブルしか
存在しなかった。ダブルだけが埋められる項目は、本番で一度も実行されない経路を作る。

境界の出力を `VerifiedSubject`（外部主体だけ）にし、内部の本人は保存側で引く。
`ResolveActorUseCase` が `UserAccountRepository.get_by_subject()` からアカウント →
本人をたどる。副次的に、「外部主体を固定していないアカウントを拒否する」判定が分岐
から消えた。`WHERE external_subject = :v` は NULL の行に当たらないので、未固定の
アカウントは検索の時点で到達できない。規約で守っていたものが仕組みで守られる。

解決の順序が「本人 → アカウント」から「アカウント → 本人」へ反転したため、本人の行が
消えている状態が新たに到達可能になった。監査の追記は本人とアカウントの両方を要求する
ので、ここで拒否する。

### ADR-47: 招待の受諾は、本人を招待から取る

`UserInvitation.accept()` は「確認済みの本人 == 招待された本人」を照合していた。
本人が境界から来なくなると、呼び出し側は `invitation.person_id` しか渡せないので、
この照合は恒真になる。恒真な判定を残すと「守られているように見えて守られていない」
表ができるため、引数ごと落とした。

消えたように見えるが、この照合は**本番では一度も効いていない**。本人IDを埋められる
実装がテストのダブルしか無かったので、境界が自分で作った値を自分で照合していた。
実際に効いている守りは受諾ユースケース側の2つで、こちらは残る。

1. 提示された外部主体が**別の本人**に束縛済みなら拒否する。招待の秘密を握っても、
   他人の主体で新しいアカウントは作れない。
2. 招待された本人の既存アカウントが停止中、または**別の**外部主体に固定済みなら拒否する。

したがって受諾の資格情報は「招待の秘密」と「その外部主体が他人のものでないこと」に
なる。`email` クレームと `InvitationAddressee` の突き合わせを足せば本物の第二要素に
なるが、`addressee` が任意項目なので全招待には課せない。必須化とセットで判断する。

### ADR-48: JWTの検証は委ね、鍵の取得は境界の向こうへ置く

署名検証・`alg` の取り違え・`crit` の扱いは、自前実装が壊れても静かに通ってしまう
領域なので PyJWT に委ねる。このアプリが持つのは使い方の側である。

- 許す署名アルゴリズムを**公開鍵方式だけに限る**。JWKSが配るのは公開鍵なので、`HS256`
  を許した瞬間に「誰でも知っている公開鍵をHMACの鍵として使う」トークンが有効になる。
  `none` も同様に受け付けない。
- `iss` / `aud` / `exp` / `sub` を必須にする。欠けたトークンを検証済みとして扱わない。
- 失敗の理由を応答に出さない。どのクレームで落ちたかは、総当たりする側に一歩ずつ正解を
  教えることになる。すべて同じ401・同じ本文へ畳む。
- 主体は `sub` だけにせず**発行元を含める**（`f"{iss}/{sub}"`）。別のIdPを足した日に
  両者の `sub` が衝突すると、他人のアカウントへ当たる。
- 鍵の取得は `SigningKeyResolver` の向こう側に置く。JWKSの取得はネットワークI/Oなので、
  ここへ直接書くとテストが実際に外へ出て、落ちた理由を実装とネットワークで切り分け
  られなくなる。本番実装は同期APIの `PyJWKClient` を別スレッドへ逃がす（そのまま待つと
  イベントループが止まる）。

`OIDC_ISSUER` という項目そのものが無ければ「接続しない」という選択として扱い、既定の
401のまま起動する。項目はあるのに空、あるいは他の項目が欠けている場合は**起動を止める**。
黙って401へ倒すと、設定を間違えた本番が「繋いだのに誰も入れない」状態で動き続け、原因が
設定ではなく実装に見える。

### ADR-49: 薬歴を中心に据え、受付NSIPS単位で記録する（分割・リフィルの特別実装は保留）

調剤薬局の実務では、レセコンや調剤機器からNSIPS（新調剤システム情報交換仕様）形式で
受付・調剤データが連携される。薬歴システムとしての自然な業務単位は「受け取った
1回の受付NSIPSデータに対して1件の薬歴を記載する」ことである。

分割調剤（長期保存困難等）やリフィル処方箋であっても、現場の実務ではレセコン側で都度受付
処理が行われ、都度の受付NSIPSデータとして連携されてくる。したがって、Dispensingや
Prescriptionの側で複数回にまたがる回数バリデーションや複雑な集約間追跡を無理に
抱え込まず、**受け取った受付NSIPS単位で1回ごとの記録として完結させる**方針を採る。

これにより、分割・リフィルの回次追跡といったDispensingの過剰な複雑化を避け、
薬歴（SOAPの充足、服薬指導、患者医療プロファイルの頭書き投影、法的3年保存要件）の
モデリングに開発リソースを集中する。

### ADR-50: 頭書きの誤登録取消と疾患状態変更も薬歴の確定時差分として投影する

患者医療プロファイル（頭書き）に登録されたアレルギー歴・副作用歴・疾患情報について、「誤登録だった」「疑いだったアレルギーが検査で否定された」「疾患が治癒・寛解した」といった事象が発生した際、頭書きを直接編集・削除することは ADR-4（薬歴からの決定的な再構築可能性）を壊すため許されない。

また、これらの事象は患者への服薬指導や聞き取りの中で判明する臨床的事実であり、真の記録である薬歴（`MedicationHistoryRecord`）に残すべきものである。

したがって、以下の設計を採用した：
1. `MedicationHistoryRecord` の `ProfileUpdateIntents` に、アレルギー取消（`retracted_allergies`）、副作用歴取消（`retracted_adverse_reactions`）、疾患取消（`retracted_conditions`）、および疾患状態更新（`updated_conditions`）を持たせる。取消には理由（`RetractionReason`）を任意で付与できる。
2. 頭書き（`PatientMedicalProfile`）は、薬歴確定時の `apply(record)` によってこれらの差分を適用し、プロファイル内の該当項目を削除または状態変更（`ConditionStatus`）する。
3. 存在しないアレルゲン・医薬品・疾患に対する取消や状態変更は、`AllergyNotFoundError`、`AdverseReactionNotFoundError`、`MedicalConditionNotFoundError` で拒否する。

これにより、頭書きの直接編集を許さずに誤登録の是正や治癒状態への更新を実現しつつ、過去の全確定薬歴からの決定的再構築（rebuild）可能性を完全に維持する。

### ADR-51: 調剤録の記載事項は号の表で持ち、他コンテキストの事実はスナップショットで運ぶ

薬剤師法第28条は調剤録の作成を義務づけ、施行規則第16条第1項がその記載事項を定める。
薬歴を調剤録の代替として使えるかは、これらの記載事項が揃っているかで決まる。

問題は、記載事項が1つの集約に収まらないことである。薬名・分量・調剤量は調剤、
交付年月日・処方医・医療機関は処方箋、氏名・年齢は患者が持つ。
しかも `[tool.import_rules.forbidden]` は薬歴ドメインから処方箋集約・患者集約への
import を禁じている。この禁止を緩めると `validate()` から他集約へ手が伸びる余地ができ、
調剤集約に対して同じ理由で置いた集約モジュール単位の禁止と矛盾する。

したがって、以下の設計を採用した。

1. 記載事項を `StatutoryDispensingRecordItem` として**号の列挙**で持ち、号ごとの
   判定関数を表に置く。表と列挙の一致はモジュール読み込み時に検査し、号を足して
   判定を書き忘れたら import の時点で落ちる。
2. 判定結果 `StatutoryRecordSufficiency` は、全号がちょうど1件ずつ現れることを
   `validate()` で要求する。表の網羅性は「判定関数が在るか」しか見ないので、
   結果を組み立てる側で号を落とせる穴が残るため、両方で塞ぐ。
3. 処方箋・患者・薬剤師の事実は不変スナップショット `StatutoryRecordSource` で運ぶ。
   全フィールドに既定値を置かず、組み立て側の書き忘れを `TypeError` で落とす。
   空の既定値は「該当なし」と区別できない。
4. 充足状態は3値（記載済 / 未記載 / 該当なし）とし、「該当なし」は源データが事由の
   不発生を積極的に示すときだけ返す。現状これに当たるのは第十号（変更調剤も疑義照会も
   起きていない場合）だけである。
5. 「薬歴が未確定」「調剤が未完了」は記載事項ではないので、表へ混ぜず
   `StatutoryRecordBlocker` として別に並べる。混ぜると「第何号が足りないのか」に
   答えられなくなる。
6. 薬歴・調剤・スナップショットが同じ1件を指していなければ、報告ではなく例外で拒否する。
   集約IDの一致だけでは足りず、法人・患者・処方箋のいずれかが食い違えば、別の調剤の
   記載事項を継ぎ接ぎした「充足」になる。
7. スナップショットは患者の同一性（`patient_id`）と患者の記載事項（氏名・生年月日）を
   **分離不能に**束ねる。分けると、そのスナップショットが本当にその患者のものかが
   呼び出し側の規約になり、別人の氏名を根拠に第一号が充足したと報告できてしまう。
   患者の氏名と年齢はスナップショットだけから判定されるので、照合を落とすと
   この判定が防ぐべきまさにその失敗が通る。

**これは報告であって強制ではない。** 記載が足りない薬歴の確定は止めない。医療機関の
所在地が未記録であることや患者の生年月日が無いことは服薬指導そのものの瑕疵ではなく、
指導記録を残せなくするほうが害が大きい。

第二号・第三号・第四号は現状の型では未記載にならない（集約の不変条件が存在を保証する）。
それでも表からは外さない。外すと調剤録の記載事項の一覧としての網羅性が失われ、
将来その項目が任意化されたときに気づけなくなる。

保険調剤録（薬担規則第10条）の保険固有項目は対象外とする。Claim / Coverage の責務であり、
到達可能な Claim ユースケースが無い間は、全件が恒久的に「未記載」を返すだけの検査になる。

### ADR-52: 疑義照会による処方変更は調剤側の参照で結び、処方箋原本の変更不可を免除する

薬剤師法第23条（疑義照会）と第24条（処方変更調剤・代替調剤・数量調整）のトレーサビリティを確保するにあたり、以下の設計判断を採用した。

1. **処方箋原本（`Prescription`）の不変性**:
   医師が発行した法的文書である処方箋原本の剤・薬品・分量を、調剤薬局側で直接書き換えることは改ざんにあたるため行わない。処方箋集約は疑義照会とその回答結果（`InquiryResultType.MODIFIED` 等）の事実のみを記録する。
2. **調剤側（`DispensingProcess`）による参照と根拠の明示**:
   疑義照会に基づく処方変更調剤は、調剤側が `SubstitutionCategory.INQUIRY_MODIFIED`（または数量調整 `QuantityAdjustmentReason.INQUIRY_AGREED`）として記録し、合意済みの疑義照会連番（`inquiry_number`）を参照することで根拠を明示する。
3. **処方箋変更制限の免除**:
   処方箋に「変更不可（`NO_GENERIC`）」が付与されている場合でも、医師との疑義照会によって合意された処方変更調剤（`INQUIRY_MODIFIED`）は処方箋の制限から**免除**される。これを `_UNRESTRICTED_SUBSTITUTIONS` として明示的に宣言し、制限対応テーブルの双方向網羅性を起動時に検証する。
4. **照会整合性の検証（`DispensingConsistencyService`）**:
   参照された疑義照会連番が処方箋に実在しない場合は `InquiryReferenceNotInPrescriptionError`（入力内容と処方箋の不整合として HTTP 422）、未回答または処方変更が合意されていない（`UNCHANGED` や `DELETED`）照会を根拠とした変更調剤は `InquiryNotAgreedError`（HTTP 422）で拒否する。
5. **処方変更を伴わない疑義照会（`UNCHANGED`）の許容**:
   照会を行った結果「原本通りの調剤で問題ない」と合意された場合、処方箋に疑義照会履歴が存在していても、調剤側は代替調剤記録なし（原本通り）で正常に調剤を進行・完了できる。

### ADR-53: 薬歴記載の区分体系を法人単位で階層管理し、SOAPの画一的必須を撤廃する

薬歴（`MedicationHistoryRecord`）は、確定時に S・O・A・P の4セクションすべてに記載があることを一律ハードコードで要求していた。しかし現場の実態（「SとPだけ記録したい」「Oは変化なしのため省略したい」「独自の生活指導や次回確認事項を記録したい」等）に合わず、運用の柔軟性を阻害していた。

したがって、以下の設計判断を採用した。

1. **画一的全節必須の撤廃と白紙確定の拒否**:
   `MedicationHistoryRecord` 単体での「S/O/A/P全4節必須」制約を撤廃し、部分的な記載（Sのみ、SとP等）でも確定できるように緩和した。一方で、記載が一切ない状態での確定・追記は `SoapContentRequiredError` で拒否し、白紙記録の発生を防ぐ不変条件を維持する。
2. **大区分・中区分の階層カタログ集約（`MedicationHistoryCategoryCatalog`）**:
   大区分（例: `soap`, `statutory`）およびそれに紐づく中区分（例: `s`, `o`, `a`, `p`, `handbook`, `residual_drug`, `concurrent_medication`, `other` 等）を法人（`CorporateId`）単位で管理する集約を導入した。
3. **法人ごとの必須ルール設定と検証**:
   中区分定義に `is_required: bool` を持たせ、法人の運用方針に応じた必須中区分（例: 「当法人ではSとPを必須とする」）を設定可能にした。薬歴確定ユースケース（`FinalizeMedicationHistoryUseCase`）は、リポジトリから法人のカタログを取得し、確定対象の薬歴が法人の必須ルールを満たしているかを検証する。
4. **追加中区分のメモ保持（`additional_notes`）**:
   S/O/A/P 以外の独自中区分や法令指導メモを構造化して保持できるよう、`MedicationHistoryRecord` に `additional_notes: tuple[CategorizedNote, ...]` を追加した。

### ADR-54: 調剤後の服薬フォローアップ記録を薬歴集約に紐づけ、頭書きへ時系列投影する

調剤・服薬指導の完了後、患者の服薬期間中に行われるフォローアップ（電話、オンライン、来局等による副作用・服薬状況・残薬等の確認および指導）の記録を保持・追記し、判明した新たな医療情報を頭書き（`PatientMedicalProfile`）へ反映する必要がある。フォローアップを別集約として切り離すと、1回の調剤・処方に対する臨床コンテキストが分断され、頭書き再構築時の由来追跡が困難になる。

したがって、以下の設計判断を採用した。

1. **薬歴集約への追記モデル（`follow_ups: tuple[FollowUpRecord, ...]`）**:
   1回の調剤・交付に対する薬歴集約（`MedicationHistoryRecord`）に、調剤後フォローアップ記録（`FollowUpRecord`）を 0〜N 件紐づけて保持する。確定済みの薬歴に対してのみ `add_follow_up()` で追加可能とし、下書きへの追加は `FollowUpOnDraftError` で拒否する。
2. **初回指導日時との時間的整合性**:
   フォローアップ日時（`followed_up_at`）は調剤時の初回服薬指導日時（`counseled_at`）以降でなければならず、過去日時の登録は `FollowUpDateBeforeCounselingError` で拒否する。
3. **フォローアップ記録の表現力と柔軟性**:
   フォローアップ記録は、通常の薬歴と同様にSOAP記述、大区分・中区分メモ（`additional_notes`）、残薬状況（`residual_drug`）、お薬手帳活用状況（`handbook_status`）、および頭書き差分（`profile_updates`）を持つ。画一的な全節必須は課さず、部分的な記載（S節のみ、あるいは電話メモのみ等）を許容しつつ、白紙の記録は `SoapContentRequiredError` で拒否する。
4. **頭書きへの投影と時系列再構築（`rebuild_from`）**:
   フォローアップで発生した頭書き差分（副作用歴・アレルギー歴・既往症更新・併用薬終了等）は、由来（`ProfileProvenance`）に元の薬歴ID・フォローアップ実施薬剤師・フォローアップ実施日を刻んで `PatientMedicalProfile.apply_follow_up()` で頭書きへ反映する。また `PatientMedicalProfile.rebuild_from()` は、初回指導日時および各フォローアップの日時を時系列昇順に並べ替えて差分を畳み込むことで、頭書きの完全な決定論的再構築を保証する。
5. **原子的永続化と境界防御**:
   フォローアップ追加ユースケース（`AddFollowUpUseCase`）は、指導者の薬剤師資格（`CounselorQualificationService`）および法人の有効状態を検証する。頭書き差分がある場合は `UnitOfWork` のもとで薬歴と頭書きを原子的に保存し、差分がない場合は頭書きリポジトリへのアクセスをスキップして不要な書き込みを抑止する。

### ADR-55: 処方医への服薬情報等提供（トレーシングレポート）および医師フィードバックを薬歴集約に保持する

薬剤師法第25条の2に基づく情報提供義務、および調剤報酬「服薬情報等提供料（1・2・3）」において、保険薬局が処方医・保険医療機関へ文書等で情報提供（残薬調整、副作用疑い、アドヒアランス不良、処方提案、患者相談等）を行った事実、および処方医からの返答内容を追跡・管理する必要がある。

調剤報酬規定（「情報提供を行った文書等の写し又はその内容を薬剤服用歴等に添付又は記載すること」「処方医からの返信等があった場合はその内容を薬剤服用歴等に添付又は記載すること」）により、トレーシングレポートおよび医師返答は薬歴と不可分に記録・保存することが法的要件である。

したがって、以下の設計判断を採用した。

1. **薬歴集約（`MedicationHistoryRecord`）への内包（`tracing_reports: tuple[TracingReport, ...]`）**:
   トレーシングレポートを独立した集約として切り離さず、薬歴集約（`MedicationHistoryRecord`）の要素として保持する。これにより、調剤・指導の臨床コンテキストとの不可分性および調剤録法定3年保存義務との整合を担保する。確定済みの薬歴に対してのみ `add_tracing_report()` で追加可能とし、下書きへの追加は `TracingReportOnDraftError` で拒否する。
2. **初回指導日時およびフォローアップ日時との時間的整合性**:
   レポート提供日時（`provided_at`）は調剤時の服薬指導日時（`counseled_at`）以降でなければならず、過去日時の登録は `TracingReportDateBeforeCounselingError` で拒否する。また、調剤後フォローアップに紐づくレポートである場合（`follow_up_id` 指定時）、そのフォローアップの実施日時以降であることを `TracingReportDateBeforeFollowUpError` で検証する。
3. **処方医からのフィードバック返答の記録モデル（`TracingReportResponse`）**:
   レポート提出後の処方医からの返答（返答日時、対応区分、内容、受領スタッフ、確認医師名）を `record_tracing_report_response()` で追記する。提供日時より前の返答日時は `TracingReportResponseDateBeforeProvidedError`、二重返答は `TracingReportAlreadyRespondedError` で拒否する。
4. **薬剤師資格とテナント認可の検証**:
   トレーシングレポート作成・報告者（`reporter_id`）は、薬剤師法第25条の2に基づく指導・情報提供の主体であるため、`CounselorQualificationService.ensure_pharmacist` による薬剤師資格の保持を必須とする。また法人の有効状態を検証し、停止中法人からの登録は拒否する。
5. **JSONB永続化の透過性と後方互換性**:
   `MedicationHistoryRecord` のフィールド追加として `tracing_reports` を導入し、PostgreSQLの `medication_history_records.payload` に透過的にシリアライズ・デシリアライズされるため、既存テーブルへの列追加マイグレーションを不要とし、過去の保存データとの後方互換性を維持する。

### ADR-39: 保存前の境界は、書く側と同じロックの内側で読む

`ManagedStaffRepository` を解体したとき、`get()` が取っていた管理ロックが
どこにも残らなかった。保存前の境界は在任中の任命を読んで検証するが、任命を書く
側と同じキーを取らないため、資格を外す保存と任命の登録が互いの確定前を読み、
どちらも成功する。資格を失ったスタッフが管理薬剤師のまま残り、例外は出ない。

ロックを `get()` へ戻すのではなく、境界の側で取る。検証が要るのは保存の経路
だけなので、参照が全ての書き込みと直列化する害を持ち込まずに競合だけを直列化
できる。この種の競合はDBなしのテストでは再現しないため、実DBの並行実行テストと、
ロック取得が読み出しより前にあることを順序で固定するテストの両方を残す。

### ADR-40: 応答モデルはドメインの語彙を持たない

Identity の DTO だけがプリミティブを保持したまま応答モデルになっており、
本人IDが `{"value": "..."}` として本文に出ていた。他コンテキストの DTO は
素の `str` なので、同じ API が項目によって違う形でIDを返していたことになる。

Application層の DTO 全般をプリミティブ禁止にはしない（内部で使う分には
ドメインの型のほうが安全）。**応答モデルとして使うもの**だけを素の型へ落とす。
境界は「外へ出るかどうか」であり、層ではない。検査も応答モデルからたどる形に
した（層で切ると、内部DTOまで巻き込んで型を弱める）。

### ADR-41: テナント最上位を法人とし、企業グループの階層は持たない

調剤薬局グループでは持株会社や複数法人体制、M&Aによる系列法人の併存が一般的だが、
システム内のテナント境界としては「法人（`Corporate`）」を最上位とし、「企業グループ
（親会社・ホールディングス）」エンティティは置かないことにした。

グループという上位概念をデータモデルに持ち込むと、「グループ内なら他法人のデータが
見えてよいか」という判断が各所に現れ、患者情報や処方データのテナント隔離が緩みやすくなる。
グループ内での法人間異動・転籍や系列別店舗の応援勤務は、ユーザー側の多対多の
アクセス権（`CorporateMembership` を複数保持する）によって自然に表現できるため、
上位組織を持たずとも業務要件を満たせる。

また、ユーザー構造も「企業グループ → 企業 → 店舗 → ユーザー」という入れ子ツリーではなく、
ユーザー（本人・アカウント）を法人の外側に独立させ、`CorporateMembership` でアクセス権を
結ぶリレーション構造とした。

### ADR-42: 管理薬剤師の在任を、店舗状態とは別の軸で新規業務に要求する

薬機法第7条は薬局ごとに管理薬剤師を置くことを義務づけるが、業務の可否は店舗状態
（`StoreStatus`）だけで判定していた。任命が1件も無い店舗、任命期間の切れた店舗でも、
`ACTIVE` でありさえすれば受付・処方箋の登録・調剤の開始・薬歴の作成が通っていた。
コンプライアンスと日々の業務が完全に切れていて、配置義務違反を抑止できない。

店舗が有効であることと管理薬剤師が在任することは別の事実なので、店舗状態の区分へ
畳まず軸を分けた。ただし宣言は業務ごとではなく**区分ごと**に置く。業務ごとに書くと、
いまは店舗状態の表と同じ値が12行並ぶだけの複製になり、片方だけ直した事故をどちらの
表も検出できない。区分を増やしたときには1行書かせる。

在任を要求するのは新規業務だけにした。不在を理由に継続業務まで止めると、調剤済みの
記録や書きかけの薬歴が不在の期間だけ凍結する。閉局で全てを止めないのと同じ理由である。
新しい業務を始めさせないことが抑止になる。判定できないときは拒否へ倒す。在任が確認
できないまま新しい調剤が始まるほうが、業務が止まるより害が大きい。

拒否は店舗状態の競合と別の例外にした。休止中の店舗と管理薬剤師のいない店舗では、
利用者が次に取る手段が違う（前者は再開する、後者は任命する）ので、同じ符号へ畳むと
分岐を書けない。

在任は任命履歴を全件読んでから絞るのではなく、業務日で1件を引く契約にした。この判定は
臨床集約を保存するたびに走る一方で、任命履歴は店舗の年数とともに増える。期間は終了日を
含む閉区間なので、最終日当日はまだ在任している。この境界は範囲型の作り方に依存し、
インメモリのダブルでは再現しないため実DBで固定した。

併せて、店舗操作の列挙から「スタッフの配属」と「管理薬剤師の任命」を外した。どちらも
列挙と区分表にだけ存在して可否の問い合わせを呼ぶ経路を持たず、表の上でだけ守られて
いるように見えていた。実際の閉局拒否は、本物の集約を受け取る Domain Service が行って
いる。境界にも同じ規則を置くと判定が2箇所になり、さらに任命を在任の要る業務として
扱うと最初の1人を任命できなくなる。

施設基準（調剤基本料の区分や各種加算の届出）は未解決のまま残っている。算定
（Claim）側の設計が先に要るので、到達可能なユースケースが無いうちは足さない。
開局時間は ADR-45 で入れた。

### ADR-43: 管理薬剤師の専任は、法人内のスタッフではなく自然人で判定する

排他制約の鍵が法人内のスタッフIDだったため、同じ人物がグループ内の別法人で
それぞれスタッフを持つと、両方の店舗の管理薬剤師を同時に務められた。スタッフIDが
違うので制約が当たらず、例外も出ない。薬機法第7条第3項の専任義務は自然人にかかる
ので、鍵の側が1段ずれていた。

任命に本人を持たせ、**法人IDを含めない**排他制約を人単位で張った。テナントを越える
制約になるので、競合したときのメッセージには相手の法人も店舗も含めない。含めると、
他法人にその人物の任命があることを知らせてしまう。知事の許可による兼務の例外は
表現しない。許可の真正性を確かめられないまま制約を緩める穴になるからである。

任命が持つ本人は対応（スタッフと本人の対応記録）の写しである。写しが対応とずれる
可能性を消すため、スタッフIDと本人の**組**で対応を参照する複合外部キーにした。
こうすると「対応の無いスタッフの任命」も「取り違えた本人」も同じ制約が弾く。
アプリケーション側でも任命の前に本人を引き、未固定なら拒否する。永続化側だけに
任せると理由の分からない失敗になるが、アプリケーション側だけに置くと、ユースケースを
通らない経路が素通りする。

スタッフ単位の排他制約は外した。複合外部キーによりスタッフIDから本人が一意に決まる
ので、同一スタッフの重複は人単位の制約が必ず捕らえる。両方を置くと、同一スタッフの
重複でどちらの制約が報告されるかがサーバ任せになり、業務例外の型が揺れる。

この変更はテーブルの形を変えるので、後続版で `ALTER` するのではなく既存の
マイグレーションの `CREATE TABLE` を直した。突き合わせの検査はマイグレーションが出す
`CREATE TABLE` の集合とスキーマ定義から生成した集合を比べるため、`ALTER` を足すと
古い形が集合に残り続けて永久に一致しない。適用済みの環境はスキーマを作り直す。

### ADR-44: 閉局の取消は状態遷移ではなく訂正として、休止へ戻す

閉局は終端状態で、操作を誤っても戻す手段が無かった。閉局と同時に管理薬剤師の任命も
当日付けで終了するので、誤操作の影響が大きい。

一方で、閉局は行政への廃止届を伴う手続きである。`change_status` で往復できるように
すると、閉局が「休止の強い版」になってしまう。取消は別の操作として分け、「その届出が
誤りだった」という訂正に限った。権限はベンダーシステム管理者専用とする。

戻す先は有効ではなく休止にした。閉局の時点で任命は終了しているので、有効へ戻すと、
取消の直後から受付だけが通って管理薬剤師のいない店舗で業務が始まる（ADR-42 で
新規業務は在任を要求するが、状態と在任は別の軸なので、状態だけを戻す設計に依存
させない）。再開は通常の状態変更として別に行わせる。

任命は復元しない。閉局中にその薬剤師が別の店舗の管理薬剤師になっていた場合、
復元すると期間が重なって専任義務に反する。取消のあとで任命し直す。

### ADR-45: 開局時間は週次の予定と特例日で持ち、判定は3値で答える

開局時間が無いと、患者への案内も電話対応も「いま開いているか」に答えられない。
時間外・夜間加算の算定にも要るが、算定側の設計を待つと、その手前の当たり前の
問い合わせにも答えられないままになる。先に「開いているか」を照会できるところまで
入れた。加算の区分は算定側の責務なので、ここでは持たない。

週次の予定は全7曜日の宣言を必須にした。宣言の無い曜日を定休日に倒すと、書き漏らした
店舗が登録できたうえで、その曜日だけ静かに閉まる。祝日・年末年始・臨時休業は日付を
指定した特例として上書きする。祝日の判定は内蔵しない。日本の祝日は法改正で変わり、
春分・秋分は毎年の天文計算で決まるので、暦を抱えるとドメインが毎年古くなる。

時間帯は終了時刻を含まない半開区間にした。資格の有効期間や管理薬剤師の任命は終了日を
**含む**閉区間だが、時刻はここで向きが違う。昼休みを挟む 9:00-13:00 と 14:00-19:00 を
閉区間で持つと、13:00 と 14:00 が2つの時間帯にまたがり、同じ時刻が開いているとも
閉じているとも言える。標準の時刻型は24時を表せないので、終端に現れた 00:00 だけを
その日の24時と読む約束にし、その約束を1箇所へ置いた。日をまたぐ夜間帯は1件で持たず
2日に分ける。1件で持つと、判定する時刻がどちらの日に属するかが時間帯の中身に依存し、
特例日の上書きも効かなくなる。

判定は真偽値ではなく3値にした。開局時間が未登録のときに「開いている」と答えると、
案内や電話対応が実在しない時刻を伝える。判定できないことを「該当しない」に倒さない
のは、医薬品マスタが無いときの麻薬区分と同じ考え方である。店舗状態が有効でなければ、
時間表に関わらず閉まっているとする。判定を状態と時間表の2箇所へ分けると、呼び出し側が
どちらかを見落とす。

日付と時刻はDomainが決めない。業務日を決めるのと同じ変換で日本時間へ揃えてから渡す。
タイムゾーンの無い日時は受け取らない。UTCのつもりの値とJSTのつもりの値が同じ形で
届き、9時間ずれた答えを黙って返すことになる。

開局時間は検索や一意性に使わないので、JSONBのpayloadにだけ置いて列を作らなかった。
既存行に項目が無くても既定値へ落ちるため、この集約に限ってはマイグレーションが要らない。
その前提はテストで固定してある。

### 残っていること

- 開発用起動点の本人ID・アカウントIDは、実在する行を指す必要がある。作成を
  助ける手順（seed）は用意していない。
- 応答の形の検査は `response_model` からたどるので、`Response` を直接返す
  ルートは対象外。いまは該当が無い。

## 2026-09-18: 操作する人を集約として持ち、権限と監査を接続した

- **種別**: アーキテクチャ判断 / ADR
- **概要**: 法人所属が変わっても維持される本人と、本人に帰属する個人アカウント、法人内の権限を3つの集約へ分けた。店舗に状態を持たせて業務の可否へ結び付け、店舗ロールの読み取りをSQL側でも絞った。業務更新と同じトランザクションに操作監査を残し、本人を特定できない更新を保存の時点で拒否することにした。

### ADR-33: 本人・個人アカウント・法人アクセス権を3つに割る

「利用者」を1つの集約で表すと、退職・再雇用・法人間の異動のたびに同じ行を作り直す
ことになり、過去の調剤録や監査がどの人を指していたのか追えなくなる。かといって
スタッフ（`Staff`）へログイン手段を持たせると、法人に属さないベンダー管理者を
表せないうえ、同じ人が複数法人で働く形を最初から閉ざす。

`AccountPerson`（法人所属が変わっても維持される人）、`UserAccount`（本人に帰属する
アカウント。外部の本人確認基盤が発行した主体と1対1）、`CorporateMembership`
（ある法人での権限と店舗範囲）に分けた。スタッフとの対応は `StaffPersonLink` を
独立した集約とし、DBのトリガと複合外部キーで別人への付け替えを封じている。
「同じ Staff を別人へ付け替えない」は業務の言葉では当たり前だが、アプリケーション側の
条件分岐で守ると、分岐を通らない経路が1つできた時点で壊れる。

代償として、1人の利用者を理解するのに4つの行を辿る必要がある。法人の利用者一覧は
権限とアカウント状態の両方を1つの公開値へまとめて返すことにした（片方だけだと
「権限は有効だがアカウントは停止中」を呼び出し側が区別できない）。

### ADR-34: 店舗ロールの制限は、権限表とSQLの取得条件の二重で掛ける

店舗の従業者に法人管理者と同じ権限を与えるわけにはいかないが、権限表だけで絞ると
「その権限を持つ」と「その店舗のデータである」が別の話になる。ユースケースが対象の
店舗IDを取らない読み取り（法人内の一覧など）では、権限表は通したうえで他店のデータが
そのまま返る。

権限の判定（`AuthorizationService`）に加えて、リクエスト単位の読取範囲を
Repositoryの取得条件へ足す形にした。取得後に絞るのではなく `WHERE` に入れるので、
件数や存在の有無からも他店の情報が漏れない。

この二重防御は、片方の既定が緩いと意味を失う。当初の読取範囲は「テーブル名と列名の
どれにも当てはまらなければ条件を付けない」という実装で、テーブルを1つ足した瞬間に
店舗ロールへ全件が見える状態になり、しかもそれを知らせるものが何も無かった。
テーブルごとの範囲を宣言制にし、宣言の無いテーブルは読めないことにした。
判断を保留できる欄を作らないのが要点で、追加したら必ず1行書かせる。

権限表そのものも、`require` と `require_store` の2箇所に同じ集合が書き写されて
いた。同じ操作が入口によって通ったり通らなかったりしうるので、判定を1つの関数に
まとめた。

### ADR-35: 店舗の状態は、業務の「開始」と「継続」を分けて止める

休止・閉局した店舗で新しい受付や調剤が始まると困るが、閉局を理由にすべてを止めると、
閉局前に始まった調剤を完了できず、記載漏れのある薬歴も直せないまま凍結する。
状態で一律に止める／止めないのどちらにも倒せない。

業務を「新規業務」「継続業務」「参照」に分類し、新規業務は有効な店舗でだけ、継続業務は
閉局していない店舗でだけ許すことにした。薬歴は、作成を新規業務、確定・訂正を継続業務と
した。

分類の表はアプリケーション側に1つだけ置く。当初は判定側が2つの集合を持ち、テストが
同じ集合を書き写して期待値を計算していた。全ての業務を列挙していたにもかかわらず、
薬歴の4操作がどちらの集合にも入っていない（=閉局店舗で新規の薬歴を作れる）という
抜けを検出できなかった。期待値を実装から導くテストは、網羅しているように見えても
実装と同時にしか壊れない。

### ADR-36: 監査は業務更新と同じトランザクションに置き、本人未特定の更新は保存の時点で拒否する

誰が何を変えたかを別系統に書くと、業務更新が確定して監査だけが落ちる形が残る。
監査を同じトランザクションの中で追記し、どちらかが失敗すれば両方とも残らないことにした。
監査行は個人アカウントへの複合外部キーを持つので、実在しない本人の記録は作れない。

この設計は「本人を特定できない更新は成立しない」という帰結を持つ。当初その判定は
トランザクションの確定直前にあったが、確定は応答を送り終えたあとに走るため、
クライアントは201と採番されたIDを受け取ってから黙ってロールバックされていた。
例外は共通の翻訳表にも届かない。判定は保存そのものの手前へ置く。そうすれば例外は
ハンドラの実行中に出て、通常の失敗として扱われる。

例外は招待の受諾で、アカウントがその操作で初めて生まれるため実行前に主体を解決
できない。こちらはリクエストのスコープではなく専用のUnit of Workから呼ぶ。

Application層にも監査の契約（`AuditedOperation` / `AuditRepository`）を置いていたが、
どこからも呼ばれていなかった。境界に見えるものが動いていないと、新しいユースケースを
そちらへ配線した人はどこにも届かない記録を書き、テストは緑を返す。削除して仕組みを
1つに保った。監査の粒度は「どの行が変わったか」のままで、退職か氏名変更かといった
業務の名前は残らない。業務名まで要るようになったら、保存経路が対象を集める箇所を
変えることになる。

### ADR-37: 操作者の識別子は Shared Kernel に置く

店舗の状態変更履歴は「誰が変えたか」を残し、Identityは法人アクセス権の範囲として
店舗とスタッフの識別子を持つ。どちらも集約間のID参照だが、そのまま所有コンテキストから
import すると Store と Identity が相互に依存し、どちらも単独では取り出せなくなる。

本人IDとアカウントIDを Shared Kernel へ置き、Identityはそれを自分の集約の同一性として
**使う**（所有はしない）形にした。薬品名を Shared Kernel に置いたのと同じ理由で、
「誰が操作したか」を要するのは Identity だけではない。店舗の状態履歴も監査も、
将来の調剤録の署名も同じ参照を必要とする。

この判断は「集約の同一性は所有コンテキストから import する」という原則と緊張する。
`PatientId` を Shared Kernel へ出す理由は無いが、操作者の識別子は複数コンテキストに
現れる語彙として例外にした。境界の向き（Identity → 店舗・スタッフ・法人は可、逆は
不可）は静的チェッカの規則として書いてあるので、この例外が次のコンテキストへ
広がることはない。

### ADR-38: 多態な値オブジェクトは判別子を保存して復元する

集約をJSONBの1列で持つ以上、抽象型のフィールドはどの具象型だったかを保存しないと
復元できない。当初は候補型を順に試して最初に通ったものを採っていたが、必須フィールドが
同形のクラスどうしが入れ替わる。実際、管理栄養士と登録販売者はどちらも登録番号1つで
表されるため、登録販売者として保存した資格が管理栄養士として復元されていた。
資格は検索列ではないので、列とpayloadの食い違いを見る検査にも掛からない。

判別子を書いて、それだけを根拠に具象型を引くことにした。区分値（`qualification_type`）は
使えない。管理栄養士と栄養士が同じクラスから返るので、クラスと1対1にならないためである。
クラス名も使わない。改名で保存済みの行が読めなくなる。改名から独立した文字列を
codecの登録簿で固定した。

判別子を持たない行は、どの型だったかを決める根拠がpayloadに無いので、別の型として
通さずに拒否する。

### 残っていること

- 権限の停止・再開は理由を受け取っていない。理由を残すなら、店舗の状態変更履歴と同じ形の
  記録を `CorporateMembership` に持たせる必要がある（操作者と記録時刻も要る）。
- 店舗の業務分類には、まだどこからも問い合わせが発生しない項目がある。分類は全て
  済んでいるので判定の穴ではないが、語彙として使われていない。
- 店舗ロール向けの開発用起動点は、本人とアカウントの行をあらかじめDBへ入れておく
  必要がある。監査の外部キーが実在する行を要求するためで、起動時に作る形にはしていない。

## 2026-09-09: 配線をDBアダプタから切り離し、束を遅延生成にした

- **種別**: アーキテクチャ判断 / ADR
- **概要**: ユースケースの配線を `app/infrastructure/postgres/` から `app/infrastructure/di/` へ移し、`postgres/` をSQLAlchemyに触る場所だけに絞った。コンテキスト束はレジストリのプロパティでアクセス時に組み立てる。

### ADR-31: パッケージ名に境界の嘘をつかせない

配線4束とComposition Rootは `postgres` パッケージに置かれていたが、SQLAlchemyを
import するのは接続を保持する `root` だけで、束は1行も触っていなかった。DBの詳細を
知らないコードが `postgres` という名前の下にいると、「このパッケージの中身はPostgreSQL
固有」という読み手の期待が外れる。同名ファイル（配線の `organization.py` とRepositoryの
`organization.py`）が並ぶ問題も、境界が曖昧なまま粒度だけ揃えた結果だった。

`postgres/` はスキーマ・接続・codec・対応・Repositoryだけにし、配線は `di/` へ出した。
これで「SQLAlchemyは `postgres/` の外に出ない」と言える状態に近づくが、`di/root.py` は
接続プールとセッションファクトリを保持するため今もSQLAlchemyを触る。禁止規則として
書けるところまでは純化していない。

### ADR-32: コンテキスト束はアクセス時に組み立てる

`PostgresUseCaseRegistry` は10束すべてを事前に構築する凍結dataclassだったが、1リクエスト
で実際に使うのは通常1束である。残り9束のために参照Boundaryの実アダプタとDomain Serviceを
毎回作っていた。プロパティで初めて組み立て、同一スコープ内でキャッシュする形へ変えた。
キャッシュの寿命はリクエストスコープと一致するので、束をまたいで状態が漏れることはない。

代償として、束の一覧が dataclass のフィールドではなくなった。配線の網羅性検査と
ルートの網羅性検査はどちらも束の一覧を型ヒントから読むので、束を足すときはレジストリ側の
登録も更新しなければ検査の対象から外れる。ここは自動導出できる余地が残っている。

## 2026-09-01: 永続化の重複を構造で潰し、フレームワーク依存を層で止めた

- **種別**: アーキテクチャ判断 / ADR
- **概要**: 集約とテーブルの対応を1つの関数へ寄せ、読み書きの経路を基底クラスに限った。Repositoryの粒度は1集約1ファイル、ユースケースの配線は束と決めた。任意項目の変換定型をApplication共通基盤へ集め、`fastapi` / `sqlalchemy` の禁止をDomainからApplication・Presentationへ広げた。

### ADR-27: 集約とテーブルの対応は1箇所に持ち、読み書きは基底経由に限る

集約をJSONBの1行として保存する設計では、同じ導出が「書き込む列」と「復元時の照合」の
2箇所に現れる。Repositoryごとに書き込みと復号を手で書いていた間は
`None if x is None else x.value` のような式が2つ並び、片方だけ直すと「保存はできるが
読み戻せない行」ができた。テーブル定義・マイグレーション・Repositoryは持ち場が分かれる
ため、この食い違いは実DBへ繋ぐまで誰も落とせない。導出は `AggregateMapping` に一度だけ
書き、書き込みと照合の両方が同じ関数を呼ぶ。

行の世代（`version`）の記録も呼び出し側の作法に委ねない。以前は記録の呼び出しを31箇所へ
書き写しており、1箇所の漏れがその経路の楽観ロックだけを静かに外していた。期待値が空の
まま保存に進むので例外も出ず、実DBで同時更新が起きるまで気づけない。記録の手続きと
`upsert` は非公開にし、公開するのは読み取り2つと保存1つだけにした。同じ理由で、世代を
覚えるときのテーブル名も既定値を持たせない。省略できると、渡し忘れた経路が別の名前空間へ
記録し、テーブル名を分けた理由（同一UUIDの別集約で世代が混ざる）がそのまま戻ってくる。

### ADR-28: Repositoryは1集約1ファイル、ユースケースの配線は束にする

粒度を揃えることには意味がないと判断した。**同じ区分で束ねる**より、**一緒に変わるものを
一緒に置く**ほうを採る。

Repositoryを業務の流れで束ねたとき、束の中に集約をまたぐコードは1つも生まれなかった。
列を導く関数はすべて単一集約専用で、束はバナーコメントで区切ったN個の独立ユニットに
なっていた。区切り線が要る時点で境界はそこにあり、ファイルがディレクトリの仕事を
していた。集約は互いに独立して変わる（処方箋の検索列を足しても調剤・薬歴は変わらない）
ので、割っても共有コードを失わない。ファイル名はRepository名から `Postgres` と
`Repository` を除いたものに揃え、集約から実装へ一意にたどれるようにした。

配線は逆に束のまま残した。こちらは `CorporateAccessService` / `Clock` / `UnitOfWork` と
いう同じ依存を配り回しており、渡すものが増えると束の中の複数のユースケースが同時に変わる。
1コンテキスト1ファイルに割った状態も試したが、importが本文の1/4を占める30行台のファイルが
並ぶだけで、探す手間だけが増えた。`medicine_catalog` を単独の束に残すのは、法人IDを取らない
唯一のコンテキストだからで、臨床の束へ混ぜるとその区別が消える。

### ADR-29: 任意項目の変換はヘルパーへ寄せる

`X.value if X is not None else None` を項目ごとに書くのをやめた。この定型は1行に収まらず
折り返されるため、項目が増えるほどDTOのフィールド構成そのものが定型に埋もれる。さらに悪い
ことに、意味のある変換（`Decimal` を `str` へ落とす等）と単なる写しが同じ見た目になり、
読み手が注目すべき箇所を見分けられない。寄せたあとに残る条件式は、判定対象と取り出す対象が
ずれる本物の条件だけになる。

定義はApplication共通基盤に1つだけ置く。各コンテキストへ複製すると正規化ルールが分岐する。
共通基盤は標準ライブラリだけに依存させる規則があるので、`DomainPrimitive` を直接受けず
`value` を持つ構造的な型として受ける。

### ADR-30: フレームワークの禁止をDomainで止めない

`app/domain/` からの `fastapi` / `sqlalchemy` は以前から禁止していたが、`app/application/` は
内側パッケージへの依存しか見ていなかった。Domainだけを守っても、ユースケースが
`AsyncSession` や `Request` を引数で受け取れる限り「具体的なアダプタはComposition Rootから
Protocolへ接続する」という前提は成り立たない。禁止をApplication層へ広げた。

HTTP境界には `sqlalchemy` だけを禁じる（`fastapi` はHTTP境界そのものなので禁じない）。
トランザクションの開始と確定はリクエストスコープだけが持つ規約だったが、規約のままでは
ルータがセッションを掴んだ瞬間に境界が2箇所になる。禁止規則にすると、持ち込んだ時点で
静的チェッカが落とす。規則を後から消せないよう、禁止先の集合そのものをテストで固定した。

## 2026-08-30: HTTP境界を追加し、認証を接続点として空けた

- **種別**: アーキテクチャ判断 / ADR
- **概要**: `app/presentational/` にHTTPルータ・例外翻訳・認証窓口を置き、法人と店舗のユースケースを公開した。認証基盤そのものは実装せず、Protocolと「必ず失敗する既定実装」だけを置いた。

### ADR-26: 認証の未接続を、通す側ではなく落とす側に倒す

認証基盤は未実装のままHTTP境界を先に作った。ここで既定を「主体不明なら素通し」に
すると、開発中は全部動くのに、接続を忘れて本番へ出た瞬間に全法人のデータが誰でも
読み書きできる。既定実装は常に401を返し、認証基盤を接続して初めて業務操作が通る。

窓口が受け取るのはBearerトークンだけにした。`Request` 全体を渡すと、クライアントが
名乗った法人IDやロールをそのまま `ActorContext` にできてしまい、テナント境界が
リクエストボディ1つで破れる。ロールと所属法人を決めるのは実装側の責務である。
トークンの取り出しは `HTTPBearer` に任せる。自分で `Authorization` ヘッダを読むと
OpenAPI に認証方式が載らず、`/docs` から試せないAPIになる。

認証はルート単位ではなくルータ単位で要求する。ルート関数の引数に頼ると、新しい
ルートを足したときに書き忘れた1本だけが無認証で公開される。書いた本人には見えない
種類の抜けなので、OpenAPIに載る全ルートへ実際に無認証で投げて401を確かめる。
依存グラフの形ではなく振る舞いで確かめるのは、FastAPIが `include_router` の結果を
内部表現に畳むためで、構造を覗くテストはバージョンで壊れる。

例外からHTTPステータスへの対応づけは1つの表に集めた。ルータごとの `try/except` に
すると、同じ例外がエンドポイントごとに違うステータスで返る。表は基底クラスへ広く
与えるが、継承だけには任せない。`StoreNotFoundError` は `NotFoundError` ではなく
`StoreApplicationError` を継承しており、継承任せだと未検出が422で返る。取りこぼしは
全例外クラスを走査し、名前が `NotFoundError` で終われば404、`Already` / `Conflict` を
含めば409であることを強制して防ぐ。

本文の形も1つに揃えた。ドメイン由来の失敗だけを翻訳すると、FastAPI の入力検証は
`{"detail": [...]}`、未知のパスは `{"detail": "Not Found"}` のまま残り、同じ422や404で
形が食い違う。クライアントはステータスを見ても本文の分岐を書けない。項目ごとの
検証内容は捨てずに `errors` へ入れ、封筒だけを共通にした。500は翻訳しない。
`Exception` のハンドラを足すとトレースが握り潰され、原因究明のほうが高くつく。

返しうるエラーはOpenAPIへ書く。書かなければ生成クライアントは成功応答しか知らず、
失敗を型として扱えない。ここで見落としやすいのは楽観ロック衝突で、一意制約が無い
更新ルートでも409になりうる。したがって書き込みルートには一律で409を書く。

権限判定はルータへ持ち込まない。ベンダー専用かどうかはユースケースが `Permission` で
要求済みであり、ルータで先回りすると判定が2箇所になって片方だけ緩む。

## 2026-08-30: 退職を所属履歴へ書き込むことにした

- **種別**: ドメイン判断 / ADR / 不具合是正
- **概要**: スタッフの無効化に退職日を必須とし、継続中の店舗所属をその日で打ち切る。

### ADR-25: 日付なしのフラグを、日付つきの導出の内側へ持ち込まない

スタッフの無効化は在籍フラグを倒すだけで、所属期間には触れていなかった。所属の
終了日が未設定のまま残るため、退職後の日付で所属店舗を問い合わせると有効な店舗が
返っていた。

導出メソッド側で在籍フラグを見て打ち切る案は採らない。所属の問い合わせは適用日を
引数に取る導出であり、在籍フラグは日付を持たない現在の状態である。導出の内側で
フラグを見ると、退職した瞬間に**在籍していた過去日**の所属まで引けなくなる。
スタッフコードを無効化後も解放しないのは過去の調剤録・監査の追跡を守るためなので、
同じ追跡を所属の側で切ってしまっては筋が通らない。適用日ごとに決まる判定へ
日付なしの値を焼き付けない方針は、頭書きの併用薬DTOで既に採っている。

退職日は無効化の入力として受け取り、もともと日付つきである所属履歴へ書き込む。
これで導出は日付つき事実だけの全域関数のまま保たれ、退職日以前の問い合わせは
退職後も同じ答えを返す。退職日より後に開始する配属予約が残っている場合は、期間と
して成立しないため無効化を拒否する。予約を取り消すか退職日をずらすかは業務判断で
あり、集約が黙って捨ててよい情報ではない。

在籍フラグは残し、ライフサイクル方言も `active_flag` のまま変えない。退職日を集約の
フィールドとして持たせると方言が日付つき無効化へ変わるが、遡及判定が要るのは所属の
問い合わせだけであり、そこは既に日付つきである。

所属を**増やす**操作（主所属の配属・異動、兼務の追加）は無効化済みのスタッフに対して
拒否する。退職日で閉じた直後に無期限の所属を足せると、閉じた意味が失われるためである。
既存の期間を閉じる操作（兼務解除）は許可する。退職後に履歴の誤りを直せなくなるほうが
害が大きい。

## 2026-08-30: 処方削除の回答を状態へ畳んだ

- **種別**: ドメイン判断 / ADR / 不具合是正
- **概要**: 疑義照会で処方削除の回答を受けた処方箋を、回答の記録と同時に取消済へ遷移させる。

### ADR-24: 「調剤できなくなった」は導出プロパティではなく状態で表す

処方医から処方削除の回答を受けた事実は `has_blocking_inquiry` として導出できたが、
その値をどの遷移ガードも参照していなかった。回答が記録された時点で未回答は
消えるため、調剤可能へ進む経路も、調剤開始の状態検査も素通りしていた。
削除された処方を調剤できる状態にあり、安全側に倒れていなかった。

導出プロパティを各所で検査する形にはしない。調剤開始側は「未回答があるか」を
処方箋の状態に畳んだ前提で状態だけを見ており、そこへ別の導出値の検査を足すと
同じ規則が2箇所に分かれる。さらに、調剤可能へ進んだ後に照会を開始して削除回答を
受ける経路が残るため、遷移時の検査だけでは塞ぎきれない。

処方削除は処方箋そのものの無効化なので、回答の記録と同時に取消済へ遷移させる。
状態に畳めば、状態を見ている下流のガードがそのまま効く。ただし調剤済・取消済に
対しては状態を動かさず回答を事実として記録するだけに留める。渡し終えた薬を
後から取り消すことはできず、遷移を試みると回答の記録自体が失敗するためである。

`has_blocking_inquiry` は残す。取消の理由が処方医の削除なのか他の事情なのかを
区別できるのはこの導出値だけであり、状態の複製ではない。

## 2026-08-30: 一人薬剤師体制を許容した

- **種別**: ドメイン判断 / ADR
- **概要**: 調剤者と最終鑑査者が同一人物であることを、集約が拒否しない仕様へ改めた。

### ADR-23: 調剤者と鑑査者の分離は集約の不変条件にしない

調剤セッションは当初、調剤者と最終鑑査者が別人であることを構築時に要求していた。
狙いは管理薬剤師による一括代行署名の防止であり、監査上の関心としては正当である。

しかし、夜間・休日当番、過疎地の店舗、小規模店舗では、1人の薬剤師が調剤から
最終鑑査までを担う体制が現に存在し、薬剤師法もこれを禁じていない。分離を集約の
不変条件に置くと、これらの適法な体制では調剤セッションを鑑査済にできず、
システムが業務を止めてしまう。

分離を要求するかどうかは法人ごとの安全管理方針であって、調剤セッション単独で
判定できる普遍的な事実ではない。集約の `validate()` が持てるのは後者だけなので、
分離の要求を取り下げる。鑑査者が薬剤師資格を持つことは薬剤師法に根拠があるため、
Boundary から得た資格情報で確認する検証としてそのまま残す。

一括代行署名の抑止を将来ふたたび必要とする場合は、法人の方針設定を受け取る
Application層の検証として持ち込む。集約へ戻すと、方針を持たない法人の適法な
運用まで巻き添えにする。

## 2026-08-29: 共通コードを所属する層へ配置した

- **種別**: アーキテクチャ整理 / ADR
- **概要**: `app/base/` を廃止し、Domain基盤・Shared Kernel・Application共通基盤を所属する層へ分離した。

### ADR-22: 「共有されること」と「所属する層」を別の軸として扱う

従来の `app/base/domain/` と `app/base/application/` は依存方向を守っていたが、
`base` がDomain・Applicationと同列に見え、DDDのShared Kernelという語を
Applicationの例外や入力正規化にまで広げていた。また、モデリング基底と
人名・薬品・用法などの業務語彙が同じパッケージに混在していた。

そこで、Domainの技術的なモデリング基盤を `app/domain/foundation/`、
所有者のいない語彙と複数コンテキストで共有する規則を `app/domain/shared/`、
Application層の共通処理を `app/application/common/` に置く。
Shared Kernelという呼称はDomainの共有語彙と規則にだけ使う。

配置変更で依存の葉が崩れないよう、Domain基盤は個別コンテキストにもShared Kernelにも
依存せず、Shared KernelはDomain基盤にだけ依存し、Application共通基盤はDomain層にも
個別Applicationコンテキストにも依存しないことを静的import検査で強制する。

## 2026-08-29: 文書とコードの責務を分離した

- **種別**: ドキュメント設計 / ADR
- **概要**: 実装から独立した理由だけを通常の `docs/` に残し、文書体系をコードの依存先にしない。

### ADR-17: 実装の現在形を文書へ複製しない

クラス、フィールド、Repositoryシグネチャ、テストファイルの一覧は変更のたびに陳腐化し、
コードとの二重管理になる。現在形は `app/`、実行可能な保証は `tests/` と `tools/`、
開発規約は `AGENTS.md` を正典とする。文書には境界、判断理由、一次資料の解釈、
未解決事項だけを残す。

### ADR-18: 不変条件表と文書参照検査を試したが撤回する

不変条件と守り手へ安定IDを付け、コードとテストから参照し、参照先を検査する方式を試した。
しかし参照を壊れにくくしただけで、コードが散文文書の構造を知る結合は残った。
文書を編集するための参照検査が必要になる時点で、不要な依存を保守していると判断した。

### ADR-19: 上位要求は一つの目的として置き、要求・要件台帳へ形式的に分解しない

このプロジェクトの上位要求は「薬局ドメインを、技術基盤から独立したドメインモデルとして
再現する」の一つである。ここから機能名を並べた要求一覧・要件一覧を作っても、実質的には
コンテキスト一覧やコードの写しになり、判定可能性は増えない。

目的は [設計概要](README.md) に一度だけ置き、達成の判断は「正当な状態を表現できるか」
「不正な状態を適切な境界で拒否できるか」などの再現基準で行う。具体的な規則は、
責務を持つコードと、その振る舞いを固定するテストで管理する。

### 一次資料の再確認で解決した事項

- リフィル2回目以降の調剤日は、「保険調剤の理解のために」§3-1 通則の本文で
  次回調剤予定日の前後7日以内と逐語確認した
- 処方編・調剤編の薬品レコードは `薬品コード X 13 可変` と定めるため、
  `MedicineCode` に固定桁数の不変条件を置かない

### ADR-20: 不変条件カタログをテストへ移す案も撤回する

文書との結合を避けるため、不変条件・守り手・IDの一覧をPythonテストへ移す案も試した。
しかし一覧は振る舞いを実行するテストではなく、実装と通常テストから読み取れる内容の再記述だった。
一覧自体の整合性テストを増やしても、守る対象が重複カタログへ移るだけなので採用しない。

### ADR-21: OKFを廃止し、通常の設計文書だけを残す

このプロジェクトではOKF固有のメタデータ、運用ルール、予約ファイル構成を必要としない。
文書は `docs/` に置き、目的・境界・判断理由・一次資料の解釈・未解決事項だけを扱う。

コードと通常テストは、文書パス、見出し、ADR番号、文書用の不変条件IDを参照しない。
その箇所の理解に必要な理由は、外部参照なしで読めるdocstring、コメント、テスト名に書く。
この分離により、不変条件カタログと、参照先の存在を検査する仕組みは不要になった。
分離違反のうち、文書パス、ADR番号、不変条件IDという構文が安定した3形式だけは
静的検査で拒否する。見出し名は改名・削除後の古い参照を判定できず、普通の語彙とも
衝突するため検査対象にしない。

コードを読まない薬剤師や監査担当向けに一覧が必要になった場合は、現在のコードとテストから
レビュー用成果物を生成する。手書きの一覧を新たな正典にはしない。

## 2026-08-29: 医薬品マスタ（MedicineCatalog）コンテキストの追加

- **種別**: コンテキスト設計 / ADR
- **概要**:
  - `app/domain/medicine_catalog/` と `app/application/medicine_catalog/` を実装。コンテキストは10から11へ。

### ADR-14: 医薬品マスタは非テナントの版付き参照データとして持つ

「医薬品マスタもドメインにすべきか」への答えは **yes、ただし既存の全コンテキストが満たす前提を2つ破る**。

| 前提 | 薬価基準収載品目 |
| :--- | :--- |
| テナント境界（`corporate_id`）を持つ | **持たない**。国が定めるので法人ごとに違わない |
| 状態変更コマンド（`change_*`）がある | **無い**。誰も作らず編集せず、外部から取り込む |

`corporate_id` を付けて普通の集約にすると、全法人に同じ行を複製し、改定のたびに
全テナント分を更新することになる。そこで:

- `Medicine` は法人IDを持たず、`MedicineCatalogRepository` も取らない。
  `tests/domain/medicine_catalog/test_medicine.py` が「法人IDを持たない」ことを固定する。
- 取り込み・参照とも `MANAGE_MEDICINE_CATALOG`（ベンダー専用権限）で、
  `require_vendor_system_admin()` を通す。既存の全ユースケースが
  `require_active(corporate_id=...)` を通るのに対し、ここだけが例外。
- 「自局で採用している薬か」「院内製剤か」はテナントごとの判断だが、それは
  **別集約（自局採用薬）の責務**であり、このコンテキストには持たせない（未実装）。

### ADR-15: 参照マスタは時点で引く

薬価基準は定期改定され経過措置期限がある。**2026-03-31 の調剤は3月版で判定しなければならない。**

- `MedicineCatalogRepository.find_effective(identifier, as_of)` と
  `MedicineRestrictionBoundary.classify(identifiers, as_of)` は **`as_of` を必ず取る**。
- 処方箋の判定に渡すのは**交付日**であって処理実行日ではない。その処方箋が書かれた日の
  マスタで判定しなければ、過去の処方を新しいマスタで誤判定する。
- 収載期間は**終了日を含む閉区間** `[listed_on, withdrawn_on]` とする。経過措置期限は
  「その日まで使える」を意味するので、資格の `[activated_on, deactivated_on)`（半開区間）と
  同じ形にすると期限当日の調剤を誤って弾く。
- 同一薬品コードで期間が重なる行は Repository契約が原子的に拒否する。重なると、ある日付で
  引いたときに2行返り「その日のマスタ」が一意に定まらない。

**この `as_of` は既存コードの穴でもあった。** `MedicineRestrictionBoundary.classify()` に
適用日が無く、プロジェクトが `CoveragePeriod` や `active_concurrent_medications(target_date)` で
徹底していた「適用日を明示的に受け取る」がここだけ抜けていた。

### ADR-16: マスタは生の事実だけを持ち、規則の答えはアダプタが導出する

`Medicine` が持つのは剤形・効能・麻薬区分・投与量限度といった**薬価基準の事実**である。
一方 Prescription が要るのは「リフィル適用除外か」という**規則の答え**で、これは

> 貼付剤（鎮痛・消炎に係る効能及び効果を有するものであって、麻薬若しくは向精神薬で
> あるもの又は専ら皮膚疾患に用いるものを除いたもの）

というリフィルの規則が定める組み合わせであり、薬価基準の1カラムではない。

変換を `app/application/composition/medicine_restriction_adapter.py`（腐敗防止層）へ
閉じ込めた。どちらかの内側へ寄せると、薬価基準にリフィルの規則が混ざるか、
処方箋が薬価基準のカラム構成を知ることになる。

あわせて `MedicineClassification` / `MedicineRestrictionFlag` を Shared Kernel から
`app/domain/prescription/value_objects.py` へ移した。使うのは Prescription だけであり、
ADR-9 の基準（所有者がいるか）で言えば共有語彙ではなく**問い合わせ結果の形**である。

## 2026-08-28: 処方箋・調剤・薬歴コンテキストの実装完了

### ADR-9: 所有者のいない語彙は Shared Kernel へ置く

薬品名・薬品コード・用量・用法は Prescription / Dispensing / MedicationHistory の3コンテキストが必要とする。どこに置くかの判断基準を「**所有者がいるか**」とした。

- `PatientId` は Patient 集約の**同一性**であり、参照する側は必ず所有者を指している。所有コンテキストから import するのが正しい。
- 薬品名は MedicineCatalog の版付きマスタ行の同一性ではなく、処方・調剤・薬歴で共通に使う値である。カタログ未収載の持参薬やOTCも表せるため、**所有者のいない語彙**である。
- 所有者のいないものを Prescription へ置くと、MedicationHistory が「他院で買ったOTCの名前」を表すために Prescription を import することになり、依存が語彙の実態と食い違う。

→ 現在は `app/domain/shared/medicine.py`（薬品語彙）と `app/domain/shared/dosage.py`（用法語彙）に置く。用法補足（処方編 別表14）は処方箋固有なので移していない。

### ADR-10: 用量に `float` を使わない

不均等服用指示は「各回服用量の合計が1日量と厳密に一致すること」を要求する。実在する用量刻み（0.05刻み等）を `float` で表すと、この一致判定が**正当な処方を弾く**。

実測: 1〜20の整数部 × 0.05刻みの小数部で全数（6,859通り）を試したところ、**869通り（12.7%）で合計が一致しなかった**。

→ `BaseNonNegativeDecimal` / `BasePositiveDecimal` を Shared Kernel に追加し、`float` からの生成を拒否する（`Decimal(0.1)` は小数部55桁になるので桁数チェックが弾く）。Application境界では `str` で受け取る。利用者のいなかった `BaseNonNegativeFloat` / `BasePositiveFloat` は削除した。

### ADR-11: 判定できないことを「該当しない」に倒さない（fail-closed）

「その薬品が麻薬か」「投与量に限度があるか」は処方箋2次元シンボルにも電子処方箋にも含まれず、判定には医薬品マスタが要る。本システムに医薬品マスタは無い。

Boundary を定義して Fake が「麻薬ではない」と答えると、**麻薬処方箋の必須3項目チェックが常に通る**状態になる。これは `check_fake_conformance` が塞いだ「呼んでも例外にならず素通りする」穴を手作りで開けるのと同じである。

→ `MedicineRestrictionFlag` に `UNKNOWN` を明示的に持たせ、Domain Service が `UNKNOWN` と「分類が渡されていない」の両方を拒否する。

**「麻薬を含む処方箋は登録できない」という分岐は書かない。** 書くと、マスタが入ったときに消し忘れる。UseCase は常にマスタを引き、マスタが無いから失敗する、という形にした。

### ADR-12: 引換番号の一意性は受領元ごとの業務判断とする

電子処方箋の引換番号は電子処方箋管理サービスが発行する一意な番号なので、重複は二重取り込みを意味する。一方、紙処方箋の番号は医療機関ごとの採番であり、**法人内で別の医療機関が同じ番号を採番しうる**。

→ `save()` の一意性は `source_type == ELECTRONIC` のときだけ課す。「無効化後に一意キーを再利用できるか」を集約ごとの業務判断として `ACTIVE_FLAG_KEY_REUSE` に記録した既存の形と同じで、全称のルールにしない。

### ADR-13: 仕様書が Domain Service を割り当てた不変条件のうち3件は、構築が既に保証していた

実装して**変異テストで検出した**。いずれも「判定を書いても1度も真にならない」ため、AGENTS.md「定義だけで raise されない例外を残さない」に反する。

| 不変条件 | 仕様書の守り手 | 実際 | 対応 |
| :--- | :--- | :--- | :--- |
| 別表16の同一コードが薬品補足と変更制限の両方に現れない | `PrescriptionMedicine.validate()` | 2つの列挙が互いに素なので構築できない | 読み込み時の分割チェック `verify_supplement_code_partition()` へ置き換え |

## 2026-08-23: 処方箋・調剤・薬歴コンテキストの仕様先行策定と規格出典の是正

- **種別**: コンテキスト設計 / ADR / 設計文書の是正
- **概要**:
  - Prescription、Dispensing、MedicationHistoryの設計文書を先行作成した。
  - 初稿を現在の [一次資料](references/README.md) にある規格PDFと突き合わせて是正した（下記ADR）。

### ADR-1: 別表番号は規格名まで明記する

初稿は「JAHIS レコードNo.201 / 別表15」のように、**JAHIS のレコード番号と電子処方箋（処方編）の別表番号を1つの出典文字列に混ぜて**いた。JAHIS Ver.1.11 の付録別表は 別表1:都道府県コード / 別表2:年号区分コード / 別表3:診療科コード / 別表4:レセプト種別コード の4つのみで、剤形区分・薬品コード種別はレコードの備考欄にインライン定義される。別表13:剤形区分（処方）・別表15:薬品コード種別は**処方編Ver2.4 の別表**である。両規格はレコード番号を共有するが別表番号は共有しない。**出典は規格名まで書く**ことをルールとした。

### ADR-2: 薬品コード種別は `PrescriptionSourceType` に依存して検証する

上記の取り違えは実害を生んでいた。処方編 別表15 は `1:コードなし` `3:厚生省コード` `6:HOTコード` を「（未使用）」「（使用しない）」として排除しており、電子処方箋で使えるのは `2:レセプト電算` `4:YJ` `7:一般名` のみである。JAHIS（紙）は6値すべて使用可。初稿は6値を単一 enum として列挙していたため、電子処方箋に送信不能なコードを凍結できてしまう状態だった。`MedicineIdentifier`（`code_type` と `code` を不可分に束ねるVO）を導入し、`source_type == ELECTRONIC` のとき使用可能な code_type を集約が検証する。

### ADR-3: 特殊公費は `ClaimCoveragePriority` へ写さない

処方箋の公費枠は 第一/第二/第三/**特殊**（JAHIS レコードNo.27〜30）、電子レセプトの公費枠は 第一〜**第四**（`ClaimCoveragePriority` は 1..4）であり、**両者は別軸**である。特殊公費の負担者番号・受給者番号は `N20`（漢字半角混在可・数字以外可。規格サンプル `30,特－１２,１２３４５６７`）で、「各番号が8桁・7桁以上及び数字以外の公費専用」と定義されている。これを priority 4 に写すと `ClaimPublicPayerNumber`（8桁）・`ClaimPublicRecipientNumber`（7桁）の桁数不変条件を壊すため、**特殊公費は Claim へ写さない**。

### ADR-4: 頭書き（`PatientMedicalProfile`）は薬歴からの投影とする

初稿は薬歴と頭書きを1ユースケース内で連続 `save()` し「即時リフレッシュ」と記述していたが、本リポジトリに `UnitOfWork` は存在せず原子性の裏付けがなかった。永続化実装が1つも無い段階で UnitOfWork を導入するのは先回りであるため、**頭書きを投影と定義**する。真は `MedicationHistoryRecord`（`ProfileUpdateIntents` に差分を保持）であり、頭書きは全薬歴を `counseled_at` 昇順に畳み込めば決定的に再構築できる。保存順序を `save(record)` → `save(profile)` に固定し、後者が失敗した場合は再構築で回復する。**薬歴に由来しない頭書きの直接編集は禁止**（許すと再構築が成立しなくなる）。

### ADR-5: 変更調剤は単一 enum ではなく3軸で表現する

初稿の `SubstitutionCategory` は「後発品変更」「減数調剤」「一包化」「計量混合」を1つの enum・1フィールドに載せていたため、同一薬品で同時に起こるこれらを1つしか記録できなかった。また `original_medicine_code` が一包化では常に `None` になっていた。**軸1: 何を出したか**（`DispensedMedicine.substitution` 0..1、元薬品必須）、**軸2: どれだけ出したか**（`DispensedRp.quantity_adjustment` 0..1）、**軸3: どう加工したか**（`DispensedMedicine.preparations` 0..N）に分解した。加算の排他（自家製剤×計量混合、外来服薬支援料2×両者）は算定ルールであり Dispensing の不変条件から外し、Claim の責務とした。

### ADR-6: 状態と重複する導出値を持たない

- `Prescription` から `INQUIRING` 状態を削除し、`has_open_inquiry`（未回答の照会が存在するか）からの導出とした。状態として持つと「照会解決後にどの状態へ戻すか」が `status` だけでは決まらず、かつ「`INQUIRING` なのに未回答照会が0件」という矛盾が構築可能になる。
- `ConcurrentMedicationRecord` から `is_active: bool` を削除し、`ended_on` からの導出（`is_active_on(target_date)`）とした。**この `is_active` は集約ルートのフィールドではないため `tests/domain/test_lifecycle_dialects.py` の分類対象外であり、仕組みでは止まらない**点を各文書に明記した。
- `Prescription` に終端 `DISPENSED` を追加した。遷移契機は調剤編 `リフィル処方箋情報レコード(521)` の調剤終了区分であり、「総使用回数に達したこと」ではない（規格は「達していないが次回以降の調剤が不要となった場合」も終了として扱う）。

### ADR-7: 分割調剤の3類型を区別する

初稿は注9（長期保存の困難性等）・注10（後発医薬品の試用）・注11（医師の分割指示）を「2〜3回」と一括りにしていたが、回数も算定も別物である（注9は上限の定めなし、注10は実質2分割固定、注11は3回までかつ合算点数を分割回数で除する）。`DispensingProcess` に `split_reason` を追加した。あわせて、リフィル・分割の各回が別薬局で行われうることから、**本コンテキストは自局実施分のみを保持する**という前提を明記した。

### ADR-8: SOAP記録に法定ラベル付きテキスト（`LabeledNote`）を導入する

日々の服薬指導記録（SOAP）を単一の平坦な文字列（非構造化テキスト）で保持すると、個別指導（厚生局監査）時に「体調変化の確認はどこか」「残薬確認の理由はどこか」といった法定要件の記載確認に時間がかかり、見落としによる指摘リスクを招く。また、過去の特定項目（例: 過去1年間の副作用確認記録のみ）の横断検索も正規表現パース頼みになり壊れやすい。
一方で、全項目を個別の入力フィールドに強制分割すると現場の入力負担が過大になる（令和6年度診療報酬改定の記載合理化の趣旨にも反する）。
そこで、`SoapRecord` の S / O / A / P の各要素を `tuple[LabeledNote, ...]`（`StatutoryCategory` Enum ＋ 自由入力テキスト `BaseFreeText`）としてモデル化した。ラベルは任意（既定値 `GENERAL`）としつつ、UI側でのテンプレート挿入・監査時の明瞭な見読性・過去薬歴の項目別串刺し検索を構造的に両立させる。
